# Architecture

## Interpretation of roles — confirm before Phase 1
Two-level tenancy:
- **Platform Admin**: operates the SaaS, manages tenant organizations, billing, cross-tenant analytics.
- **Tenant roles** (inside one organization = one "Client"): `owner` (full access), `planner`, `engineer`, `finance`, `administratie`.

The **Clients module is the tenant's own customer records** (their CRM) — not the tenant itself. If this is wrong, flag it before Phase 1 starts: it changes the schema.

## Stack
- Next.js 15 (App Router, Server Components by default), TypeScript strict
- Supabase: Postgres, Auth (email/password + magic link, SSO later), Storage, Row Level Security
- Stripe: Billing (subscriptions, per-module price items), webhooks → entitlements
- Vercel: hosting, preview deployment per PR
- Design system: `@yourorg/ui`, an npm workspace package living in this same repo at `packages/ui` (not a separate repo/registry) — see "Design system consumption" below

## Multi-tenancy & data isolation
- `organizations` = tenants
- `platform_admins` — separate from tenant roles (e.g. `users.is_platform_admin boolean`), never assignable through tenant-facing invite flows
- `memberships (user_id, organization_id, role)` — role enum: `owner | planner | engineer | finance | administratie`
- Every tenant-scoped table carries `organization_id`. RLS policy pattern — implemented (see `supabase/migrations/20260822150910_organizations_memberships_baseline_rls.sql`) via a `SECURITY DEFINER` helper function rather than an inline scalar subquery:

```sql
-- Helper (defined once, in the baseline migration). SECURITY DEFINER lets it
-- read `memberships` bypassing RLS, which is what avoids "infinite
-- recursion detected in policy" when used inside memberships' own policies,
-- and also avoids "more than one row returned by a subquery" if a user is
-- ever a member of more than one organization (a plain scalar-equality
-- subquery breaks in that case).
create or replace function public.is_member_of_org(org_id uuid)
returns boolean
language sql stable security definer set search_path = public
as $$
  select exists (
    select 1 from public.memberships m
    where m.organization_id = org_id and m.user_id = auth.uid()
  );
$$;

-- Every tenant-scoped table's policy:
create policy "org_isolation" on assets
  using (is_member_of_org(organization_id));
```

  Use `is_member_of_org(organization_id)` (and, where a write should be owner-only, `is_org_owner(organization_id)`) in every new tenant-scoped table's RLS policies — don't re-derive membership with an inline subquery.
  - **Tenant activate/deactivate** — `organizations.is_active boolean not null default true`, added in `supabase/migrations/20260826120000_organizations_is_active.sql` (issue #47). `is_member_of_org`/`is_org_owner` were extended in that same migration to additionally require `o.is_active` on the target organization (join to `organizations`, same signatures, no caller changes needed anywhere) — this single choke point makes an entire deactivated tenant's data invisible/unwritable under RLS to that org's own members, across every tenant-scoped table that already calls one of these two helpers, with zero per-table changes. `organizations_select_creator_or_member`'s `created_by = auth.uid()` branch deliberately does **not** require `is_active` (unaffected, since it doesn't call either helper) — the Platform Admin who created a tenant org via `activateAsTenant` must still see/manage that row while deactivated, in order to reactivate it. `memberships_select_self_or_same_org`'s `user_id = auth.uid()` self-visibility branch was also updated in that migration to require the row's own org to be active (checked directly against `organizations`, not `memberships`, so it doesn't reintroduce the same-command MVCC recursion issue `20260822173916_fix_memberships_self_visibility.sql` fixed) — otherwise a deactivated org's member could still read their own membership row via that bypass. Reactivating (`is_active = true`) restores exactly the prior access; deactivate/reactivate never mutates membership rows themselves. The deactivate/reactivate Server Action and login-time gate are `auth-rbac-engineer` follow-ups on top of this column; the UI button/badge is a `frontend-ui-engineer` follow-up.
  - **`current_member_role(org_id uuid) returns membership_role`** — added in `supabase/migrations/20260823120000_work_orders_core.sql` (issue #13), `SECURITY DEFINER`/`stable` like the two helpers above. Returns the caller's role in `org_id`, or `NULL` if they have no membership there at all. `is_member_of_org`/`is_org_owner` only answer yes/no questions; once a table's RBAC matrix row needs a real 3+-way split (e.g. `work_orders`: owner/planner full, engineer assigned-rows-only, finance/administratie read-only-all-rows), policies branch on `current_member_role(organization_id) in (...)` / `= 'engineer'` instead of stacking more boolean helpers. Reuse this for Assets' own still-deferred Planner/Engineer split and for a future Contracts table's Finance-CRUD boundary — don't reinvent a role check inline.
- No client-side query ever bypasses RLS. Server actions run under the user's session. The service-role key is used only in trusted server-only contexts (billing webhook sync, audited platform-admin cross-tenant reads). Platform Admin cross-tenant reads are **not** implemented as an RLS bypass policy for `is_platform_admin` users — they go through `lib/supabase/admin.ts` (service-role) from trusted server code only, audited in application code.

### Auth flows — implemented (issue #3)
- `lib/auth/session.ts`: `getCurrentSession()` / `requireSession()` resolve the signed-in user, their `is_platform_admin` flag, and their (first) organization + tenant role in one place, under the caller's own session. `app/(app)/layout.tsx` calls `requireSession()` to gate the entire authenticated route group (redirects to `/login` when signed out); nothing else under `app/(app)` needs its own "is anyone signed in" check.
- `lib/auth/actions.ts`: Server Actions for signup, login, logout, invite creation, and invite redemption — all via `lib/supabase/server.ts` (never `admin.ts`). This Supabase project requires email confirmation (`mailer_autoconfirm: false`), so a brand-new signup has no session in the same request; organization/owner bootstrap is deferred to that user's first successful login (see `ensureOwnOrganizationBootstrapped` — carries the org name through via Supabase user metadata across the confirmation round trip).
- `app/(auth)/{login,signup,invite/[token]}`: route group without the `AppShell` chrome (sibling to `app/(app)`), using `@yourorg/ui` form primitives (`Input`/`Label` — see `packages/ui`, "Design system consumption" below).
- Invite mechanism: see the `invites` table entry under "Core schema (current)" above.

All sync/creation triggers are `SECURITY DEFINER`, letting an engineer's own `time_entries`/`work_order_articles` write (which they DO have RLS rights for) transitively write `quote_line_items` (which they do NOT). Sync stops permanently once a quote is promoted (`is_auto_draft -> false`) — the Work Order's "Create Quote" button (`app/(app)/work-orders/create-quote-actions.ts`) now promotes the existing auto-draft instead of always inserting a new quote, falling back to a from-scratch quote only when no auto-draft exists (e.g. a legacy pre-migration work order). Application-layer surfaces built on top of this schema: a Settings > Billing > Default Rates page (owner-only write) for `organizations.default_travel_article_id`/`default_work_article_id`; the Work Order Hours section and "To invoice" KPI tile now read the auto-draft's frozen totals (`getWorkOrderCostSummary`) instead of recomputing live, gated to roles with `planning`/`read` (excludes engineer, who still sees duration-only); an unresolved-rate warning (`getUnresolvedWorkOrderTimeEntries`); and the `/quotes` list filters out `is_auto_draft` quotes by default (toggle to reveal, "Concept" badge). See `docs/SCHEMA-HISTORY.md` for the full design writeup.

RLS is **deliberately narrower than, and role-different from, `quotes`' own** — only `current_member_role(organization_id) in ('owner', 'administratie')` may SELECT/INSERT/DELETE; no planner/engineer/finance access at all, matching issue #119's explicit "owner / administratie" framing (Platform Admin is covered for free by being an `owner` of their own Platform org — no platform-admin-specific RLS clause). `invoice_number` (format `INV-<year>-NNNN`, e.g. `INV-2026-0184`) is minted by `next_invoice_number(organization_id)` — the exact structural precedent of `next_asset_display_id`/`asset_id_sequences` (`20260831090000_assets_auto_generate_asset_id.sql`), a per-organization counter table (`invoice_number_sequences`) advanced atomically via `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, race-safe under concurrent generation; unlike `next_asset_display_id`, this function IS `grant execute ... to authenticated` (a Server Action calls it directly, not a trigger) so it re-checks the owner/administratie role itself and raises `42501` otherwise. `pdf_path` is a Storage object path in the new PRIVATE `invoices` bucket (`{organization_id}/{quote_id}/invoice.pdf`, no public SELECT policy at all — unlike the public `client-logos`/`avatars` buckets — every Storage operation gated on `current_member_role((storage.foldername(name))[1]::uuid) in ('owner', 'administratie')`); the app mints short-lived signed URLs server-side for the "view in a centered popup" UI. PDF rendering itself (reading the quote's line items/client/totals plus `organizations.own_client_id` for the tenant's own company data, issue #120) is `api-backend-engineer`'s follow-up, out of scope for this schema-only migration.

### Tenant-configurable reference data (picklists)
**Implemented** in `supabase/migrations/20260822200000_reference_lists.sql`, tested in `supabase/tests/database/reference_lists_rls.test.sql`. Generalizes "Asset Type" / "Asset Status" (and every tenant-configurable dropdown since) into one reusable pattern instead of a hardcoded enum (can't gain a per-tenant value without a migration) or free text (no governance):
- `reference_lists (id, organization_id, list_key, name, created_by, created_at, updated_at)` — one picklist container per `(organization_id, list_key)`, e.g. `list_key = 'asset_type'`. `list_key` is plain text (not an enum) specifically so a brand new picklist never needs a schema migration to introduce, only a data-seeding change.
- `reference_list_items (id, reference_list_id, organization_id, value, label, color, sort_order, is_default, created_by, created_at, updated_at)` — the individual selectable values within a list (e.g. `value='hvac', label='HVAC'` inside the org's `asset_type` list). `value` is a stable machine slug (unique per list); `label` is the tenant-editable display text. At most one item per list has `is_default = true` (enforced by `enforce_single_default_reference_item` + a partial unique index) — used to auto-fill e.g. `assets.status_id` when a caller omits it on insert.
- **Pattern choice**: a generic reference-list pattern (one schema/RLS/seed-trigger surface shared by every picklist) was chosen over dedicated tables per concept, since more of these keep arriving and this codebase has shipped the grant-lockdown boilerplate wrong before (see `docs/SCHEMA-HISTORY.md`'s baseline section) — minimizing how many times that boilerplate gets written is a real risk reduction. The trade-off: every query against a picklist's items is one join deeper than a dedicated table, and there's no per-concept FK typing (nothing at the schema level alone stops pointing `assets.type_id` at an `asset_status` item) — closed instead by a `validate_*_reference_items` trigger on the referencing table.
- **`organization_id` denormalization**: `reference_list_items.organization_id` is denormalized from `reference_lists.organization_id` (via `reference_list_id`), kept in sync by the `derive_reference_list_item_org` trigger, so RLS stays a single-column `is_member_of_org(organization_id)`/`is_org_owner(organization_id)` check with no in-policy joins. `reference_list_id` is NOT re-parentable — excluded from the UPDATE column grant entirely.
- **RLS**: SELECT is `is_member_of_org(organization_id)` (any role — every Select dropdown in the app needs this); INSERT/UPDATE/DELETE is `is_org_owner(organization_id)` only — same write boundary as `clients`/`sites`/`assets`.
- **Seeded defaults on organization creation**: `seed_default_reference_lists(organization_id)` (idempotent, `on conflict do nothing` throughout) is called automatically by an `after insert on organizations` trigger (`organizations_seed_reference_lists`, `SECURITY DEFINER`), so every new organization gets its starting picklists with zero application-layer effort. **Any future tenant-configurable picklist should extend `seed_default_reference_lists` with another `list_key` block plus a one-time backfill call in that feature's own migration — do not invent a new seeding mechanism.**
- **What a client needs to query**: to populate a "select asset type" dropdown — `GET /reference_list_items?select=id,value,label,sort_order,is_default&reference_lists!inner(list_key)&reference_lists.list_key=eq.asset_type&order=sort_order` (RLS scopes it to the caller's own org automatically). To let an owner add a new value — first `GET /reference_lists?select=id&list_key=eq.asset_type` to get that org's list id, then `POST /reference_list_items` with `{ reference_list_id, value, label, sort_order? }` (as an `is_org_owner` session; `organization_id` is derived automatically and must not be supplied).

### Dependent reference lists (generic capability)
**Implemented** (issue #26) in `supabase/migrations/20260823090000_contacts_dependent_reference_lists.sql`. A reference list's valid items can depend on which item was picked from another list (e.g. Asset Sub-type depends on Asset Type) — this is a standing case per "Domain completeness" below, not a one-off:
- `reference_lists.parent_list_key text` (nullable) — when set, declares that every item in THIS list must belong under an item from the list with `list_key = parent_list_key`, in the same organization. Plain text, not a FK, because `list_key` alone isn't unique (uniqueness is `(organization_id, list_key)`) — resolving "which list" is organization-scoped and done inside the validation trigger, not declaratively. Insert-only in the client-facing grants (a list's dependency is a fixed structural property).
- `reference_list_items.parent_item_id uuid references reference_list_items(id)` (nullable) — required, and validated, exactly when the item's own list has a non-null `parent_list_key`. Enforced by `validate_reference_list_item_parent`: rejects a missing `parent_item_id` when required, a parent from the wrong `list_key`, or a parent from a different organization.
- Generic and reusable, not hardcoded to any one pair — confirmed by a second pilot (`sla_tier` depending on `contract_type`) after the first (`asset_subtype` depending on `asset_type`). A list-level dependency check (`validate_reference_list_item_parent`) only guarantees the item is a valid child in the abstract `reference_list_items` graph; a genuine cross-field dependency (e.g. an asset's `subtype_id.parent_item_id` must equal that same asset's own `type_id`) still needs one small addition to the referencing table's own `validate_*_reference_items` trigger, same shape each time.

For exactly which tables/migrations exercise this pattern, and the full column-by-column history of every implemented table above, see `docs/SCHEMA-HISTORY.md`.

**Implemented** (issue #4): `lib/rbac/permissions.ts` encodes the table above verbatim as `TENANT_PERMISSIONS` (+ a `PLATFORM_ADMIN_PERMISSIONS` column), exposing `can(actor, module, action)`, `canAny(...)`, `allowedActions(...)`, and `canAccessModule(...)`. `actor: { role: TenantRole | null; isPlatformAdmin?: boolean }` keeps Platform Admin as an orthogonal flag, never a `TenantRole` member, per the rule above. `_own`-suffixed actions (`create_own`/`read_own`/`update_own`) mark matrix cells like "Read (assigned)"/"Read/Update/Create own" — callers must still apply the actual resource-ownership filter themselves; `can()` only tells you the verb is allowed at all.

**"Invoices" vs "Billing/Facturatie" — these are two different rows, not a duplicate.** "Invoices" (module key `invoicing`, issue #119) is the actual, narrow, shipped capability: a button on a Quote's detail page generates a PDF invoice from that quote (line items/client + the org's own company data, issue #120); the invoice can be viewed and deleted, never updated (delete + fresh insert to regenerate). "Billing/Facturatie" (module key `billing`) is still exactly what it always was — an unimplemented placeholder from the original matrix (no `app/(app)/billing` page/actions exist, and `billing` is not in `lib/rbac/features.ts`'s `SHIPPED_FEATURES`) reserved for a future, broader tenant billing/payment-tracking module. Don't merge these two rows/keys without deliberately deciding what happens to `finance`'s CRUD on the `billing` placeholder — issue #119 intentionally excludes `finance` from `invoicing`.

Which migration made which matrix row real RLS (not just `can()`-only), and why each shape was chosen, is logged in `docs/SCHEMA-HISTORY.md`'s "RBAC matrix rollout, by migration" section — check there before assuming a row is still `can()`-only.

- Collapsible sidebar (persisted per user), command palette, optimistic mutations
- View switcher per module: list / kanban / calendar / map (Assets, Planning)
- Skeleton loading, not spinners; route-level streaming (Suspense)
- Design tokens and components come exclusively from `@yourorg/ui` — no ad-hoc styling in the app repo

### Relational detail pages — the standard, not a special case
A flat list + a create/edit modal is never the whole answer once a record has real relationships (a client has sites and assets; a contract will have line items and linked assets; a work order will have a client, a site, an asset, and a planner). Whenever you build or touch a detail page for an entity that has related child or parent records, apply this pattern:

- **Surface the relationship in place.** A parent detail page shows its related records as tabs (`Tabs` from `@yourorg/ui`), not just a link out to another module's list. Reference implementation: `app/(app)/clients/[id]/client-detail.tsx` — a client's own fields, plus `Sites` and `Assets` tabs on the same page, with `SitesPanel`'s per-site asset count jumping straight into the matching `Disclosure` group in `AssetsPanel`. That three-level hierarchy (client → sites → assets) staying visible and navigable from either tab, instead of being flattened into one generic table, is the bar — not the exception.
- **Create in context.** A record creatable from a parent's tab (e.g. adding an asset from a client's Assets tab) should open pre-scoped to that parent (client/site already set), not dump the user into a bare, disconnected form.
- **Nested groupings use `Disclosure`**, not a flat table, once a list has a natural sub-grouping (assets grouped by site, line items grouped by category, etc).
- **Breadcrumb the hierarchy**, don't just "back link" it. `BackLink` (single hop, "back to X") is right for a page with one obvious parent list. Once a page sits two or more levels deep in a real hierarchy (Clients → Acme Corp → Site X), it needs a breadcrumb trail showing the full path, not just a single hop backward — add a `Breadcrumbs` primitive to `@yourorg/ui` if one doesn't exist yet rather than approximating it with more `BackLink`s.
  - **Breadcrumbs render in the Topbar, not inline in the page body.** The mechanism is `usePageHeader()` (`components/shell/page-header-context.tsx`): a page calls `usePageHeader(<Breadcrumbs items={...} />)` (the element built with `useMemo`, keyed on its real inputs — see that hook's own doc comment for why an un-memoized element causes an infinite render loop) and it renders in `Topbar`'s title slot instead of scrolling away with `<main>`. Every top-level entity detail page is wired this way now — `client-detail.tsx`, `clients-explorer.tsx` (kanban view only), work orders, quotes, and (issue #107) assets and contracts. A record-editing form that's a slide-in panel (see "Popup vs. full page" above) never needs this at all — it isn't a page, there's nothing to breadcrumb.

Before building a new module (Contracts, Planning, Reporting — see `docs/ROADMAP.md`), identify its real relationships first and design the detail page's tabs/breadcrumbs/nesting up front — don't ship the flat version now and "add relations later."

#### Two detail-page header patterns — pick by content shape, not habit
As of issue #107, there are deliberately **two** header/layout patterns for a top-level entity's detail page, not one. Which pattern a page uses is a content-shape decision, not a leftover-vs-migrated one — pick per the rule below, and see `docs/DESIGN-SYSTEM.md` for the designer-facing version of this same rule.

**Pattern A — `RecordHeroBand` + flat sections** (`packages/ui/src/components/record-hero-band.tsx`, plus `RowCard`/`RelationCard`/`SectionHeader`/`KeyValueList`/`SummaryRow`/`StatStrip`). Originated in the Work Order redesign (#102/#103/#106); Assets and Contracts adopted it in #107. A full-bleed dark hero band — badges above a large serif title, an icon+text `meta` row, right-aligned `actions` — rendered as the page's very first element (a sibling BEFORE any `Card`, not nested in one), followed by `RelationCard`s for the record's direct relations and flat `SectionHeader`-led sections for its own field/log content, **with no enclosing `Card`** around those sections. Use this pattern for **operational records whose detail page is dominated by the record's own working content** (a compact field set, a log of hours/material, a checklist) rather than by navigating to sibling records. `RecordHeroBand`'s own doc comment states directly why it isn't a dark variant of `DetailHero`: "the two have almost no shape in common... beyond both being the header of a detail page."

**Pattern B — `DetailHero` + `DetailLayout`** (`packages/ui/src/components/detail-hero.tsx`). The original "Option C" editorial header — an initials hero mark (`Avatar` `size="lg"`, a 56px rounded-square with a serif-face initial), the entity's name as `Heading level={1}`, a dot-separated `meta` line, `badges` appended after — paired with `DetailLayout`'s 340px sticky rail of plain `Card`s and a `Tabs`-driven main column. Used by Quotes, kept there deliberately: a **relationship-light** record (mainly its own line items, one Notes card) that still wants the rail-plus-tabs shell rather than Pattern A's flat stacked sections. This is not an unfinished migration; a future story could still move Quotes to Pattern A if the product direction changes, but until then treat it as intentional.

**Clients — a deliberate hybrid, not a third pattern to generalize.** `app/(app)/clients/[id]/client-detail.tsx` pairs Pattern A's `RecordHeroBand` (dark full-bleed header, with a `StatStrip` baked into the band — the "relationship info in the blue header" the product owner asked for) with Pattern B's `DetailLayout` rail (Company/Platform/Locations-map/Notes cards) and `Tabs` (Sites/Assets/Contacts/Work Orders/Contracts/Quotes/Activities) below it. Reasoning: a client is both an operational record with its own header-worthy facts AND the app's single most relationship-heavy, tab-driven record — it doesn't fit either pattern's pure form. The rail's old "Relationship" card (a `DefinitionList` "Client since" + counters) was removed once its content moved into the header, rather than kept as a duplicate. **Issue #113** then found the hero `StatStrip` had drifted into just re-stating each tab's own `(count)` suffix (Sites/Assets/Orders/Quotes/Meldingen counts) — pure duplication, not new information — and replaced it with facts that live nowhere else on the page: Account Manager, an active-contracts count + value, an open-work-orders count with its next-scheduled date, and the most recent Activiteit's date/type. The same story also moved the platform-admin-only "Access"/"Modules" tabs off this page's own `Tabs` into a small Edit-popup on the rail's Platform card (`platformDialogOpen`/`PlatformDialogTab` in `client-detail.tsx`) — they'd been competing for tab-strip space with the client's real relational tabs despite being a management surface, not one of the client's own relationships; see "Popup vs. full page" above for why that popup, not a page, is the right container. Don't read any of this as license to freely mix-and-match components between the two patterns elsewhere — this combination exists because Clients' content genuinely needs both halves, confirmed by explicit product-owner direction, not because any two components can be combined. A hero `StatStrip` tile, generally: pick facts not already visible as a sibling tab's own `(count)` label — restating a tab count in the hero is exactly the anti-pattern issue #113 fixed.

- **Reference implementations**: Pattern A — `app/(app)/work-orders/components/work-order-screen.tsx` (origin), `app/(app)/assets/[id]/asset-detail.tsx`, `app/(app)/contracts/[id]/contract-detail.tsx`, `app/(app)/activities/components/activity-screen.tsx` (issue #118). Pattern B — `packages/ui/stories/EditorialDetailPage.stories.tsx` (generic template) and `app/(app)/quotes/[id]/quote-detail.tsx` (real implementation). Hybrid — `app/(app)/clients/[id]/client-detail.tsx`.
- **Client-specific addition, not part of the generic Pattern B rail**: the Sites tab's `.ui-sites-grid` layout (table + a narrow "Locations" map side-card, `app/(app)/clients/[id]/sites-panel.tsx`) is specific to Clients (and any future address-bearing entity) — it is not something a new Pattern B (or hybrid) page should expect to inherit just because it uses `DetailLayout`.

#### Overview-page header pattern (issue #116, rollout complete)
Detail pages have used the full-bleed dark-fjord band since #102/#103/#107 (Pattern A above); issue #116 brings that same visual language to a module's OVERVIEW/list page too — "change the page header to the blue header used on work order items," applied one module at a time. The primitive is **`OverviewHeroBand`** (`packages/ui/src/components/overview-hero-band.tsx`), not `RecordHeroBand` reused as-is: `RecordHeroBand`'s props (an inline-editable title input, a breadcrumb-style `recordLabel`/`recordCode`, `badges`, `meta`, an `assignee` block, a full-width `StatStrip`) are shaped for a single record and don't fit a list page's own content (a static page title, an optional subtitle, a small inline stat readout, and right-aligned `ViewToggle`/primary-action controls). `OverviewHeroBand` reuses the same full-bleed mechanics and dark-surface token overrides (`background: var(--ui-brand-fjord)`, the `--ui-fg`/`--ui-muted`/`--ui-border`/badge-tint re-pointing, the negative-margin trick that cancels `--ui-page-inset-x/y` so the band sits flush to the viewport/sidebar/topbar edges) but with its own smaller prop shape: `title`, `subtitle`, `stats` (an inline right-aligned KPI readout, distinct from `RecordHeroBand`'s bottom-edge `StatStrip`), and `actions`. Same rule as `RecordHeroBand`: render it as the page's very first element (a sibling BEFORE any `Card`), and keep anything that wants the light "sheet" look — a page's search/filter row — in a normal `Card` sibling BELOW the band, not inside it. Reference implementation: `app/(app)/clients/components/clients-explorer.tsx` (both List and Kanban views render one `OverviewHeroBand` — Kanban additionally passes its "Klanten"/"Pipeline potential" readout into the `stats` slot — followed by a plain `Card` holding the search/filter controls). **All seven top-level overview pages are now converted** — Clients (title+`stats`+`actions`, per the reference implementation above), and Assets, Contracts, Articles, Work Orders, Quotes, and Meldingen (each a plain `title`+`subtitle` band, since their toolbar/create-button/view-switcher chrome streams in async inside their own `*Screen` component's `Suspense` boundary rather than being available synchronously in the Server Component page shell — only the static title/subtitle chrome moved into the band on these six, their `Toolbar`/create-button/filters/view-switcher stayed exactly where they were, rendering below the band).

### Popup vs. full page — pick by weight, not habit
A `Dialog` is for a **small, secondary list's** create/edit form — a sub-entity reached from a tab on some other record's detail page (Contacts on a client, Sites on a client, an item in a Settings reference list). It is **not** the right pattern for a top-level module's own primary record.

- **Top-level module entities** — Contracts, Planning/Work Orders, and future Sales/Ops modules like Quotes or Projects/Orders (see `docs/ROADMAP.md`) — get a **real page** for create/edit, not a modal, by default. These records carry enough fields, relationships, and (once Work Orders/Contracts land further) enough sub-content of their own that a popup is the wrong container — a page gives room to breathe, a real URL to link/bookmark, and space for the record's own tabs/sections without nesting a `Tabs`-inside-a-`Dialog`. Clients and Assets are explicit, product-owner-confirmed exceptions to this default — see below.
- **Work Orders — a third variant of "real page," not a separate route per state (issue #89, "New workorder en edit workorder scherm gelijktrekken"):** `/work-orders/new` is still its own route (create genuinely has no id yet), but the old separate `/work-orders/[id]/edit` route is gone — an existing work order's own fields (title, client/site/asset/contract, assignment, schedule, status/priority) are inline-editable directly on the detail page (`app/(app)/work-orders/[id]/page.tsx`, via `WorkOrderScreen`/`WorkOrderHero`/`RecordHeroBand` — see "Two detail-page header patterns" above, Pattern A), right alongside its Hours/Material/Checklist/Assignment sections — never a navigation away to a dedicated edit screen. Each section renders its fields read-only for a caller without `update`/`update_own` on `planning`, so the one page serves both a viewer and an editor without a second route. The same story also converted Time Entries' "Add"/edit from `Dialog` popups to inline editable rows (`WorkOrderHoursSection`) for the same "avoid an unnecessary popup/route hop" reasoning. Treat this as the pattern for a top-level entity whose detail page already has enough room for its own fields, not as license to silently retrofit Contracts/Quotes the same way without similar product-owner framing. (Issue #107 gave Assets and Contracts this same header/section pattern for consistency — that did not touch this section's popup-vs-page rule itself: Clients/Assets below still get the slide-in-panel treatment for create/edit, unchanged. Activities used to be listed here too — see the note at the end of its own bullet below for why it no longer is.)
- **Explicit, confirmed overrides — Clients and Assets, so far**: for these two top-level entities specifically, the product owner has explicitly asked for the slide-in-panel treatment instead of a real page, for both create and edit.
  - **Clients**: issue #43 ("Nieuwe klant toevoegen toont nieuwe popup") moved client CREATE to `NewClientPanel` (`app/(app)/clients/new-client-panel.tsx`, a `Dialog` `size="panel"`), deleting the old `/clients/new` route. Issue #46 ("Client edit pagina moet ook een slide in popup worden") did the same for client EDIT — `EditClientPanel` (`app/(app)/clients/edit-client-panel.tsx`) replaced the old full-page `/clients/[id]/edit` route (also deleted; `ClientForm`/`client-form.tsx`, that page's form component, was removed too since the panel was its only remaining caller). Both panels are opened from local component state (`client-detail.tsx`'s own `useState` on the client's own detail page; a lifted `editTarget`/`onEdit` state pair in `clients-explorer.tsx`, mirroring the existing `deleteTarget`/`onDelete` pattern, for the clients list/kanban).
  - **Assets**: issue #53 ("Als gebruiker wil ik een asset kunnen toevoegen", acceptance criterion "Asset edit pagina is omgebouwd als slider popup") explicitly asked for the same treatment. `AssetFormDialog` (`app/(app)/assets/components/asset-form-dialog.tsx`, a `Dialog` `size="panel"`) replaced the old full-page `/assets/new` and `/assets/[id]/edit` routes (both deleted, along with that page's form component, `asset-form.tsx`) — a prior version of this doc flagged the (then-full-page) asset form as a "known gap" pointing the other direction; issue #53 resolved it by making Assets a deliberate second carve-out instead. Every trigger (`CreateAssetButton`, the asset detail page's `AssetDetailActions`, the list/table row-level Edit actions in `AssetsTable`/`SiteAssetsTable`) opens the dialog from local component state, same pattern as Clients above.
  - **Activities (historical — reversed by issue #118, see the note at the end of this bullet)**: 2026-08-28 feedback ("Edit activity pagina, maar ook de new activity pagina is niet lekker ingedeeld... gebruik hier maar slider popup voor") asked for the same treatment a third time. `ActivityFormPanel` (`app/(app)/activities/components/activity-form-panel.tsx`, a `Dialog` `size="panel"`) replaced the old full-page `/activities/new` and `/activities/[id]/edit` routes (both deleted, along with that page's form component, `activity-form.tsx`). Same self-fetching-on-open shape as `AssetFormDialog` (an outer component owning `useActionState`, an inner body — remounted fresh every open — owning every other piece of local state and a mount effect that fetches every picklist/locked-record it needs), so every trigger (`CreateActivityButton`, `ActivitiesTable`'s row click/Edit, `ActivitiesPanel`'s row click) stays a thin trigger with local `open` state, no page-level prop-threading required. Issue #90 ("Activity create aanpassen") then consolidated this further: there used to be a second component, the read-only `ActivityQuickViewDialog`, opened on a row click, with its own `ActivityFormPanel`-in-edit-mode nested on top of it for a caller with edit rights — two screens for what's really one record. That dialog is now deleted; a row click opens `ActivityFormPanel` itself in `mode: "edit"` directly, which renders every field read-only (`Badge`/`DefinitionList`/`Text`, no `<form>`, no Save — the same shape `WorkOrderFields`'s own `readOnly` branch uses, issue #89) for a caller without edit rights on `activities` (a `finance`/`administratie` viewer), and the normal editable form otherwise. Delete (reusing `DeleteActivityDialog`) and a prominent "Create work order" call-to-action (an accent-toned `Card` near the top of the panel body, gated on `canCreateWorkOrder` — issue #87 — deliberately not just another equal-weight footer button) moved from the deleted quick-view into `ActivityFormPanel` itself, `mode: "edit"` only, so both actions stay available everywhere the panel opens from a row click — including the Client detail page's Activiteiten tab (`clients/[id]/activities-panel.tsx`), which has no row-level Delete button of its own and relies entirely on the panel's. **Issue #118 (2026-09-02, "Activity scherm omgebouwd naar standaard scherm") reversed this**: the product owner asked for Activities to move OFF the slide-in-panel treatment and onto a standard full detail page instead — `ActivityFormPanel` is deleted, replaced by `app/(app)/activities/[id]/page.tsx` + `app/(app)/activities/new/page.tsx`, both rendering the shared `ActivityScreen` (`app/(app)/activities/components/activity-screen.tsx`), following the Work Order "real page, inline-editable, no separate edit route" pattern described above (Pattern A — see "Two detail-page header patterns"). Kept here, unremoved, as an accurate record of what shipped and why at the time — not as a currently-active carve-out.
  - Treat Clients and Assets as named, specific carve-outs — not a precedent to silently extend to Contracts/Work Orders/Quotes/Activities without the same explicit product-owner sign-off.
- **A record-editing form that becomes a panel has no breadcrumb of its own to worry about** — see the note on `Breadcrumbs` placement below (Topbar via `usePageHeader`, not inline per page). This is one more reason the popup treatment simplifies a top-level module's create/edit surface, not just a UX preference: a full page needs its own breadcrumb trail computed and threaded through; a slide-in panel, opened from wherever the caller already is, doesn't.
- **Sub-entities reached from a tab** (Contacts, Sites) stay dialogs — they're small, single-purpose, and scoped to a parent that's already on screen; a full-page round trip would be overkill for them.

### Row and tab-panel conventions — consistent layout across relational detail pages (issue #113)
Two small conventions, codified after the Clients detail page ("Indeling Clients/id") audit found them applied inconsistently across its own Sites/Contacts/Assets tabs. Apply both to every relational detail page's tabs (Clients today; any future record with the same "tab of related rows" shape), not just Clients.

- **Badge before content, not after.** Any row that pairs a name/address/label with a status badge (a "Primary" site or contact row, a tenant-status line, etc.) renders the badge FIRST, then the text — e.g. `<Inline gap="xs" align="center">{isPrimary && <Badge variant="accent">Primary</Badge>}<Text>{address}</Text></Inline>`, not the reverse. This keeps every such row scannable the same way regardless of which tab/panel it's in. Reference: `app/(app)/clients/[id]/sites-panel.tsx`'s site-name cell, `contacts-panel.tsx`'s contact-name cell.
- **On a `RecordHeroBand`, badges live in `meta`, not the `badges` prop.** A first correction here said the component-level `badges` prop (its own row above the title) needed no change — product feedback on the shipped Clients page overturned that: badges (Primary/status/tenant, whatever the page has) belong in the `meta` row, as its FIRST item wrapped in `<span className="ui-record-hero-band-meta-badges">…</span>`, so they sit on the same line as the address/other meta facts, below the title — not on their own row above it. This is the same placement Work Orders already uses for its status/priority pair (issue #106, `work-order-hero.tsx`). Reference: `app/(app)/clients/[id]/client-detail.tsx`'s `heroMeta`. Treat `RecordHeroBand`'s `badges` prop as effectively deprecated for new pages — reach for a `meta`-row badges span instead.
- **Tab-panel "Add X" button.** A tab panel's own "add a new related record" action is a `SectionHeader` (`icon` + short title matching the tab's own icon/label, e.g. "Sites"/"Contacts"/"Assets") with the add action in its `actions` slot as a small primary `<Button variant="primary" size="sm">+ Label</Button>` — never a bare full-width `<Inline justify="end">` with no heading above it. A first correction here moved this to `variant="outline"` to mirror Work Orders' "+ Article"/"+ Travel"/"+ Work" (`work-order-material-section.tsx`, `work-order-checklist-section.tsx`) exactly; product feedback reverted the color back to `"primary"` (the accent/yellow treatment) while keeping the rest of that shape — small size, `SectionHeader` placement, "+ Label" text. Applies specifically to a **tab-panel-level** add action on a relational detail page (Sites/Contacts/Assets/Activiteiten/Work Orders/Contracts tabs on Clients today) — it does NOT apply to `EmptyState`'s own action button (that stays as-is, it has no row/grid above it to sit beside) or to a top-level module's own default-size primary "Create X" action (Work Orders' "New Work Order," the Assets module page's own "New Asset" toolbar button, etc.), which keep their existing treatment per "Buttons: default size vs. small" in `docs/DESIGN-SYSTEM.md`.
- **A `SectionHeader` title with no add action is still correct when a tab genuinely has none.** The Quotes tab gets the same `SectionHeader` (icon + "Quotes") for title consistency, deliberately with an empty `actions` slot — a manual "New Quote" entry point exists elsewhere (`CreateQuoteButton`, `/quotes/new`) but is intentionally not surfaced on this tab (most quotes arrive via a Work Order's auto-draft, issue #109, not a bare click from the client page). Applying the row/header *shape* everywhere doesn't mean every tab needs an add button — that's still a per-tab, product-owner call.
- **A tab-panel "add" button reuses the target module's existing client-scoping mechanism, not a new one.** Work Orders' "+ Work order" (`work-orders-panel.tsx`) opens the exact same `NewWorkOrderPickerDialog` the standalone Work Orders overview's own "New work order" button already uses (issue #106), via `CreateWorkOrderButton`'s existing `clientId` prop, which locks/pre-fills the picker's Client field. Contracts' "+ Contract" (`contracts-panel.tsx`) opens the real `/contracts/new?clientId=…` create page the same way, via `CreateContractButton`'s existing `clientId` prop. Neither needed a new create surface — both buttons are the tab-panel-convention shape wrapped around a trigger component that already supported client pre-scoping.

## Domain completeness

`docs/BUSINESS-PLAN.md` §4 was widened 2026-08-23 after review: the original module list only had each module's MVP slice (e.g. a client with one email/phone, no contact persons) instead of the realistic domain a premium comparable product has. This is now a standing requirement, not a one-time fix:

- **Before modeling a new module or entity**, briefly research 1-2 comparable premium SaaS products in that domain (ServiceTitan/Jobber/Housecall Pro/Salesforce Field Service-tier, or the closest equivalent for a non-FSM concern) and default to that realistic breadth of sub-entities/fields, not the minimum needed to satisfy the current user story. `docs/ROADMAP.md` names the modules already identified this way (Work Orders, Contacts, Quotes, Invoicing, Preventive Maintenance, Inventory, Customer Portal, etc.) — check there first before assuming something is out of scope.
- **Every categorical/type/status field is tenant-configurable** via `reference_lists`/`reference_list_items` (`supabase/migrations/20260822200000_reference_lists.sql`) — never a hardcoded enum or free text.
- **Check whether a reference list depends on another one** before modeling it as a flat list — e.g. Asset Sub-type's valid values depend on which Asset Type is selected. Use the dependent-list mechanism (`reference_lists.parent_list_key` + `reference_list_items.parent_item_id`, validated the same way `validate_asset_reference_items` validates cross-list correctness) instead of one flat list mixing every possible value, or instead of inventing a one-off parent/child table pair.
- **A picklist item outgrows `reference_list_items` once it needs more than one dependency, or a typed field of its own** — the dependent-list mechanism above is single-parent (one `parent_list_key` per list), and `reference_list_items`' generic value/label/color/sort_order/is_default shape has nowhere to hang a second/third relationship or an extra column without polluting that shared table for every other `list_key` that doesn't need it. Precedent: `asset_models` (`supabase/migrations/20260826160000_asset_brand_and_models.sql`) — a Model needs Brand + Type + Sub-type simultaneously, plus `default_warranty_months` — so it's a dedicated table, not a `reference_list_items` row, while still reusing every other reference-list convention (`organization_id` checked by RLS, owner-configures/any-member-reads, a `validate_*_reference_items` cross-field trigger mirroring `validate_asset_reference_items`'s structure).
- **New sub-entities follow the "Relational detail pages" standard above**: surfaced as a `Tabs` entry on their parent, created in-context, not bolted on as a disconnected flat list reachable only via its own top-level route.

## Design system consumption
`@yourorg/ui` lives in this repo at `packages/ui`, as a real npm workspace package (root `package.json` `"workspaces": ["packages/*"]`), not a separate repo or private registry — there is no separate design-system repo, and none is planned for now. This is a deliberate choice, not a temporary stand-in (that was the old `vendor/yourorg-ui-stub`, now deleted): keeping it in-repo means the app and its design system iterate in the same PR.

- **Package structure**: TypeScript/TSX source in `packages/ui/src`, built with `tsup` to `packages/ui/dist` (both compiled JS — ESM + a CJS fallback for non-Next tooling — and generated `.d.ts` declarations straight from the `.tsx` source, so component implementations themselves are type-checked, not just call sites). `dist/` is gitignored, never committed — it's a build artifact, same as `.next/`.
- **The app still only ever imports from `@yourorg/ui`** / `@yourorg/ui/icons` / `@yourorg/ui/styles.css` (CLAUDE.md rule 4 is satisfied by this package boundary) — never reach into `packages/ui/src` or `dist` directly.
- **Build wiring**: `npm run build`/`npm run typecheck` at the root each have a `pre*` script (`prebuild`/`pretypecheck`) that builds `packages/ui` first, since the app consumes it like a normal dependency (needs `dist/` to exist), not via source transpilation. `npm run dev` has an equivalent `predev` step. CI (`.github/workflows/ci.yml`) builds `packages/ui` explicitly before lint/typecheck/build for the same reason.
- **Two "use client" boundaries**: `ThemeProvider`/`useTheme` and `Tabs` are the only stateful/interactive primitives in the package; everything else is a plain presentational function so it stays safe to render from Server Components. See the top-of-file comment in `packages/ui/tsup.config.ts` for why those two need their own dedicated build entries (a real, empirically-discovered esbuild/RSC directive-bundling gotcha, not incidental complexity).
- Fixes/changes to a component go into `packages/ui` directly, in the same PR as the app change that needed them — there's no "upstream repo" to send them to anymore.
- **Pattern A primitives** (issue #102/#103/#106, generalized beyond Work Orders in #107 — see "Two detail-page header patterns" above): `RecordHeroBand` (full-bleed dark hero band), `RowCard` (a bordered row for a log-like list — hours, material, checklist items), `RelationCard` (a compact "linked record" card — icon, eyebrow label, name, one-line subtitle, optional Edit), `SectionHeader` (icon + serif title + divider + trailing actions), `KeyValueList` (a full-width label-left/value-right row list for a record's own facts), `SummaryRow` (a `RowCard`-list's totals footer), `StatStrip` (the KPI-tile strip baked into `RecordHeroBand`'s bottom), `Callout` (an icon + copy warning-toned box, e.g. for a record's Notes). `docs/DESIGN-SYSTEM.md` has the designer-facing guidance on when to reach for each.
