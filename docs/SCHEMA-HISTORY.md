# Schema history

This is the chronological, per-migration log of how the database schema, RLS
policies, and the RBAC matrix's per-module rows evolved — moved out of
`docs/ARCHITECTURE.md` (issue #65) so that doc stays a lean reference for
standing patterns and conventions instead of growing without bound as every
migration lands. This file is the changelog; `docs/ARCHITECTURE.md` is the
pattern reference. For the exact SQL and RLS tests, follow the referenced
`supabase/migrations/*.sql` and `supabase/tests/database/*.sql` files; for
the product-owner story behind a change, follow the referenced issue number.

When a new migration lands, append a new bullet/section here rather than
growing `docs/ARCHITECTURE.md`'s schema section again. If a migration
introduces a genuinely new, reusable *pattern* (not just another table), that
pattern description belongs in `docs/ARCHITECTURE.md` instead — this file is
for "what changed and why," not "how the standing mechanism works."

## Baseline: organizations, memberships, users
- `organizations`, `memberships`, `users` (Supabase `auth.users` + profile table) — **implemented** in `supabase/migrations/20260822150910_organizations_memberships_baseline_rls.sql`:
  - `users (id uuid pk references auth.users, email, full_name, is_platform_admin boolean default false, created_at, updated_at)` — profile row auto-created by an `on auth.users insert` trigger; `authenticated` only has column-level UPDATE grant on `full_name` (never `is_platform_admin`/`email`/`id`), so no client path can self-elevate to platform admin. **`avatar_path`/`avatar_updated_at`/`locale` added** by `supabase/migrations/20260826140000_user_profile_avatar_locale.sql` (issue #49, "Personal profile management") — no new table, no new RLS policy needed (the existing `users_update_self` row-level policy already scopes to `id = auth.uid()`; only the column-level UPDATE grant was extended). `avatar_path text null` is a Supabase Storage OBJECT PATH (not a full URL) in the new public `avatars` bucket, e.g. `{user_id}/avatar.webp` — null means no photo (UI shows initials fallback). `avatar_updated_at timestamptz null` is trigger-stamped (`set_avatar_updated_at`, BEFORE UPDATE, mirrors the `created_by`/`checked_by`+`checked_at` trigger-stamp pattern) to `now()` only when `avatar_path` actually changes, kept separate from the general `updated_at` so the app can cache-bust the public avatar URL (`?v=<epoch>`) precisely on photo changes, not on unrelated edits like a name change — excluded from the client-facing UPDATE grant (trigger-only, like `created_by`). `locale text not null default 'nl' check (locale in ('nl','en'))` is a stored UI-language preference; deliberately a plain CHECK constraint, not a `reference_lists` entry, since it's a fixed 2-value system constant (not tenant-configurable business data) — there is no i18n/translation system in the app yet, this column only stores the preference for future wiring. Both `avatar_path` and `locale` are granted on UPDATE (not `avatar_updated_at`).
  - **Storage: `avatars` bucket** — the first Storage usage in this repo (`supabase/migrations/20260826140000_user_profile_avatar_locale.sql`), setting the convention for any future bucket. `storage.buckets` row: `public = true` (headshot photos, not sensitive tenant data — served via plain `<img src>`, no auth header, like a typical SaaS avatar CDN URL). `storage.objects` RLS: ownership is enforced by PATH PREFIX, not a DB owner column — `(storage.foldername(name))[1] = auth.uid()::text` requires an object's name to start with `{auth.uid()}/` for that user to INSERT/UPDATE/DELETE it (`avatars_insert_own_folder`/`avatars_update_own_folder`/`avatars_delete_own_folder`); SELECT (`avatars_select_public`) is open to `public`, matching the bucket's own public flag. Reuse this exact path-prefix-ownership pattern for any future per-user (not per-org) Storage bucket.
  - `organizations (id uuid pk, name, slug unique, created_by references users, is_active boolean default true, created_at, updated_at)` — visible to its creator (`created_by = auth.uid()`) even before any membership exists (needed for `INSERT ... RETURNING` during signup bootstrap), and to any member thereafter. **`is_active`** added by `supabase/migrations/20260826120000_organizations_is_active.sql` (issue #47) — see `docs/ARCHITECTURE.md`'s "Tenant activate/deactivate" bullet under "Multi-tenancy & data isolation" for the full RLS mechanism.
  - `memberships (id uuid pk, user_id references users, organization_id references organizations, role membership_role not null, created_at, updated_at, unique(user_id, organization_id))` — `role` enum: `owner | planner | engineer | finance | administratie`.
  - Bootstrapping (first org + first owner membership on signup): a user may self-insert an `owner` membership into an organization only if (a) they created that organization and (b) it has zero existing members. After that, only existing `owner` members can insert further memberships — this is the hook the invite flow (issue #3/#4) should use.

## Clients, Sites, Assets, Account Managers
- `clients`, `sites`, `assets` — **implemented** (issue #7) in `supabase/migrations/20260822190000_clients_sites_assets.sql`, tested in `supabase/tests/database/clients_sites_assets_rls.test.sql`:
  - `clients (id, organization_id, name, kvk_number, vat_number, iban, notes, status, account_manager_id, potential_value, client_since, won_at, created_by, created_at, updated_at)` — the tenant's own customer records (their CRM), not the tenant itself. `organization_id` is supplied directly by the inserting owner (checked by RLS, like `invites.organization_id`). **Its original flat `address_line1`/`address_line2`/`postal_code`/`city`/`country` columns were dropped** by `supabase/migrations/20260825090000_sites_addresses.sql` (issue #41 redo) — `sites` (below) is now the sole, multi-address model for a client's address(es); see that bullet. **`email` dropped, `kvk_number`/`vat_number`/`iban` added** by `supabase/migrations/20260825150000_clients_business_fields.sql` (issue #43, "Breid client uit") — a client's contact email now comes from a `contacts` row (`contacts.email`) or isn't tracked at the client level; `kvk_number` (Dutch Chamber of Commerce number), `vat_number` (VAT/BTW number), and `iban` (bank account IBAN) are plain `text` with no DB-layer format validation. **`represents_organization_id`** (nullable, unique-when-set FK into `organizations`, `on delete set null`) was added by `supabase/migrations/20260825160000_clients_represents_organization.sql` (issue #45, "Platform Admin managing tenants by reusing the Clients module") — when set, this Client row IS a real platform tenant: the Platform Admin operates as an `owner` member of a dedicated "Platform" organization (bootstrapped by hand, not by this migration) and manages tenants as `clients` rows within that org, same as any tenant manages its own CRM clients; `activateAsTenant` (`app/(app)/clients/actions.ts`) creates the linked `organizations` row and sets this column. No new/changed RLS policy was needed — `clients_update_owner`'s `is_org_owner(organization_id)` check is keyed on the client row's OWN (Platform) `organization_id`, which the Platform Admin already owns, exactly like any other client update. Granted on UPDATE only (not INSERT) — a client is never created already representing a tenant. **`phone` dropped** by `supabase/migrations/20260826130000_sites_phone.sql` — moved to `sites.phone` (below); a client can have multiple sites, each with its own contact number, so phone belongs on the physical location, not the client record. **`status`/`account_manager_id`/`potential_value`/`client_since`/`won_at` added** by `supabase/migrations/20260827100000_clients_kanban_status.sql` (issue #58, "Als gebruiker wil ik een kanban bord hebben voor mijn klanten") — replaces the old placeholder stacked-cards kanban (`app/(app)/clients/kanban.ts`'s `groupClientsForKanban`) with a real drag-and-drop board driven by a stored column: `status text not null default 'lead' check (status in ('lead','qualified','proposal','won'))` is the kanban's 4 fixed columns, deliberately a plain CHECK (not a `reference_list_items` FK) since the 4 stages are fixed by the story itself, not tenant-configurable; `account_manager_id uuid null references account_managers(id) on delete set null` (validated same-organization by `validate_client_account_manager`, see the `account_managers` bullet below) is the client's default Account Manager shown on its kanban card; `potential_value numeric(12,2) null check (potential_value is null or potential_value >= 0)` is a potential deal amount (explicitly not "ARR" per the product owner); `client_since date null` has no DB default — the app defaults it to today only on CREATE, never auto-fills on edit (pure UI-layer logic); `won_at timestamptz null` is **not** in the client-facing INSERT/UPDATE column grants — it's maintained entirely by the `set_client_won_at` trigger (`before insert or update of status`), which sets it to `now()` the moment `status` BECOMES `'won'` and clears it back to `null` the moment `status` changes AWAY from `'won'` ("became Won" semantics — re-entering Won later restarts the clock, not "was ever Won once"; staying `'won'→'won'` or moving between two non-`'won'` statuses leaves it untouched). The kanban's "Won" column only shows clients that became Won in the last 4 weeks — that windowing is application-layer (list query/grouping), not RLS; `won_at` (partial index, `where won_at is not null`) exists to serve that query. No new/changed RLS policy needed — all five columns are covered by the existing `clients_insert_owner`/`clients_update_owner` (`is_org_owner(organization_id)`) policies, same reasoning as `represents_organization_id` above.
  - `account_managers (id, organization_id, first_name, last_name, created_by, created_at, updated_at)` — **implemented** (issue #58) in `supabase/migrations/20260827090000_account_managers.sql`, tested in `supabase/tests/database/account_managers_rls.test.sql`. A deliberately minimal, org-scoped named-person list (first name + last name only, nothing else) whose only purpose today is to populate the "Account manager" picker on a Client (`clients.account_manager_id` above) — **not** an extension of real org-member/login accounts (`users`/`memberships`); there is no members/invite-management Settings page in this app yet, and the product owner's own description ("Die gebruikers zijn nog vrij leeg, alleen Voornaam Achternaam") was explicitly about this standalone list, not real auth accounts. Modeled exactly like `asset_models`: `organization_id` supplied directly on insert, checked by RLS; `created_by`/`updated_at` trigger-stamped the same way. **RLS/grants**: identical shape to `asset_models`/`reference_lists`/`checklist_templates` — SELECT any org member; INSERT/UPDATE/DELETE owner only (Account Managers are managed from Settings by the owner). **Still open, for `frontend-ui-engineer`/`api-backend-engineer`**: a Settings-tab manager UI (list + create/edit, same shape as the Asset Model manager) and `lib/account-managers/{schema,actions}.ts` server actions gated on the `settings` module; and wiring `clients.status`/`account_manager_id`/`potential_value`/`client_since` into `ClientRecord`/`clientCreateSchema`/`clientUpdateSchema`/`createClient`/`updateClient` plus the actual drag-and-drop kanban board UI replacing `groupClientsForKanban`.
  - `sites (id, organization_id, client_id, phone, address_line1, address_line2, postal_code, city, country, latitude, longitude, geocoded_at, notes, is_visit_address, is_invoice_address, is_delivery_address, is_primary, visit_contact_id, delivery_contact_id, invoice_contact_id, created_by, created_at, updated_at)` — a client's physical location, and (as of `20260825090000_sites_addresses.sql`, issue #41 redo, "Sites as client addresses") the client's address book: a first pass of that story built a brand-new `client_addresses` table before being corrected — `sites` already served this role (it's also the location `assets` hang off of via `assets.site_id`; that dual role is intentional, not split apart). `latitude`/`longitude` are plain `double precision` (no PostGIS dependency) — sufficient for map-view pins; revisit only if geospatial queries (radius search etc.) are actually needed. **Repurposed by that same migration** from manually-entered coordinates to a server-computed geocoding cache: `geocoded_at timestamptz` (nullable) records when they were last computed from the address fields by `lib/geocoding/nominatim.ts` (free, no-API-key OSM Nominatim search), written by the `createSite`/`updateSite` server action, not a DB trigger — "the pin follows the address," not manual lat/long entry. **`name` column dropped** by `supabase/migrations/20260825120000_sites_drop_name.sql` (issue #42) — a site is identified purely by its formatted address everywhere in the UI now (e.g. "Vleutenseweg 22, Utrecht"), not a free-text label; the column-level INSERT/UPDATE grants were already re-issued without `name` in that same migration (Postgres drops a column's own grant entries automatically on `DROP COLUMN`, so no separate `revoke` was needed). **`phone` added** by `supabase/migrations/20260826130000_sites_phone.sql` — moved from `clients.phone` (a client's phone now lives on the site/location it belongs to, not the client record); plain nullable `text`, no DB-layer format validation, granted on both INSERT and UPDATE (unlike `clients.represents_organization_id`, a site's phone is a normal field settable at creation time).
    - **Purpose flags**: `is_visit_address`/`is_invoice_address`/`is_delivery_address` booleans (visit address/invoice address/delivery address) — a row-level CHECK (`sites_at_least_one_purpose`) requires at least one true per site. Every site that existed before this migration was backfilled `is_visit_address = true` (a site was already, by construction, a place a technician visits). **Cross-row invariant, deliberately NOT DB-enforced**: across ALL of a client's sites, each of the three purposes must be covered by at least one site (a single site may cover more than one) — this is a per-client aggregate check a plain row CHECK can't express; it's `api-backend-engineer`'s responsibility in `createSite`/`updateSite`/`deleteSite` to reject a write that would leave a purpose uncovered for that client.
    - **`is_primary`**: at most one `true` per `client_id` — the client's main address, badged in overviews/detail pages. Enforced by `enforce_single_primary_site` (auto-unsets the previous primary on INSERT/UPDATE OF `is_primary`) plus `sites_one_primary_per_client_idx` (partial unique index), mirroring `contacts.is_primary`/`enforce_single_primary_contact` exactly.
    - **Legacy-address backfill**: every client with a non-null legacy `address_line1` and no existing `sites` row got exactly one new site (`name = 'Main address'`, all three purpose flags true, `is_primary = true`) created from that data before the flat columns were dropped from `clients`. A client that already had sites AND a non-null flat address had that flat data dropped, not migrated (judgment call — no reliable way to know which existing site it corresponded to).
    - **Contact persons per purpose** — `visit_contact_id`/`delivery_contact_id`/`invoice_contact_id` (added by `supabase/migrations/20260826150000_sites_contact_persons.sql`, issue #52) are nullable FKs into `contacts`, `on delete set null` (deleting a contact clears the reference on any site that pointed at them — it neither blocks the delete nor cascade-deletes the site). Each, when set, must belong to the SAME `client_id` as the site itself, not merely the same organization — enforced by `validate_site_contact_persons` (`before insert or update of client_id, visit_contact_id, delivery_contact_id, invoice_contact_id`, same structural style as `validate_asset_reference_items`/`validate_contact_role_item`, `23514` on a same-org-different-client or cross-org mismatch). "Required when the matching purpose flag is true" is deliberately **not** a DB CHECK (no sensible backfill value existed for pre-existing sites) — it's an application-layer rule (Zod schema + `createSite`/`updateSite` server actions). No RLS policy change was needed — `sites_insert_owner`/`sites_update_owner` key only on `is_org_owner(organization_id)`, not individual columns.
  - `assets (id, organization_id, client_id, site_id, name, type_id, subtype_id, external_reference, brand_item_id, model_id, serial_number, status_id, installed_at date, warranty_until date, notes, created_by, created_at, updated_at)` — equipment installed at a site. `type_id`/`status_id` are FKs into `reference_list_items` (see `docs/ARCHITECTURE.md`'s "Tenant-configurable reference data" pattern) — **as of `20260822200000_reference_lists.sql`**, these replaced the original free-text `type` column and the original `asset_status` enum column (`'active'|'decommissioned'`), because a Postgres enum cannot gain a per-tenant value without a schema migration and free text has no governance at all. `status_id` defaults to the organization's default `asset_status` item when omitted on insert (same UX the old `default 'active'` had); `type_id` is required, no default, same as the old `type` column. `subtype_id` (nullable FK into the dependent `asset_subtype` list, see "Dependent reference lists" in `docs/ARCHITECTURE.md`) was added by `20260823090000_contacts_dependent_reference_lists.sql`. **`manufacturer`/`model` (free text) were dropped and replaced by `external_reference`/`brand_item_id`/`model_id`** by `supabase/migrations/20260826170000_assets_external_reference_brand_model.sql` (issue #53): `external_reference text null` is a plain ungoverned free-text field (the tenant's own external/legacy reference number, e.g. from an ERP or previous system — same shape as `notes`/`serial_number`, no FK); `brand_item_id uuid null` is a FK into `reference_list_items` scoped to that org's `asset_brand` list (see "Asset Brand + Asset Model" below); `model_id uuid null` is a FK into `asset_models`. Both are nullable (Brand/Model are not required at the asset level). `type_id`/`status_id`/`subtype_id`/`brand_item_id`/`model_id` are all validated by one extended trigger, `validate_asset_reference_items` (`before insert or update of type_id, status_id, subtype_id, brand_item_id, model_id`): each of `type_id`/`status_id`/`subtype_id`/`brand_item_id` must resolve to a `reference_list_items` row with the matching `list_key` (`asset_type`/`asset_status`/`asset_subtype`/`asset_brand` respectively) in the asset's own `organization_id` (`23503` if dangling, `23514` on wrong `list_key` or cross-org); `subtype_id` is additionally cross-checked against the asset's own `type_id` (its `parent_item_id` must match); `model_id` must resolve to an `asset_models` row in the asset's own `organization_id` (`23503`/`23514`) but is deliberately **not** cross-checked against the asset's own `type_id`/`subtype_id`/`brand_item_id` — auto-filling those from a selected model is a UI convenience, not a DB invariant, since a user can legitimately pick a Model and still correct e.g. its Type for one mis-catalogued unit.
  - **`organization_id` denormalization decision**: `organizations -> clients -> sites -> assets` is a 2-3 hop chain. Rather than write RLS policies that join through `clients` (and, for `assets`, through `sites` *and* `clients`), both `sites` and `assets` carry their own `organization_id` column (and `assets` also carries `client_id`, denormalized from its `site_id`), so every tenant-scoped table keeps the same simple, single-column `is_member_of_org(organization_id)` / `is_org_owner(organization_id)` RLS policy shape — no in-policy joins, cheaper to plan. These denormalized columns are populated automatically by a `BEFORE INSERT/UPDATE OF <parent-fk>` trigger (`derive_site_organization_id`, `derive_asset_org_and_client`) and are **excluded from the client-facing column-level INSERT/UPDATE grants** (same lockdown pattern as `invites.token`/`accepted_at`) — callers must supply `client_id` (sites) / `site_id` (assets) only; the trigger derives and overwrites `organization_id`/`client_id` regardless of what's sent. The same triggers also reject any UPDATE that would re-parent a row across organizations (raises `23514`), since a plain RLS `USING`/`WITH CHECK` on `organization_id` alone can't express "and don't let this row move to a different tenant."
  - **Write RLS boundary (v1, deliberately coarse)**: SELECT is `is_member_of_org(organization_id)` (any role) on all three tables. INSERT/UPDATE/DELETE is `is_org_owner(organization_id)` only, on all three tables — this matches the RBAC matrix's "Owner: CRUD" column but does **not** yet implement Planner's "Read/Update" or Engineer's "Read/Update (assigned)" on Assets at the RLS layer; that finer split is an application-layer (`lib/rbac/permissions.ts`) concern until Phase 2's assignment-based scoping lands. A Planner/Engineer session cannot write these tables directly today — non-owner writes (once built) must go through a server-side path that checks `can()` and uses the service-role client.
  - `created_by` on all three tables is trigger-stamped (`set_created_by`, `auth.uid()`) and excluded from client-facing grants, same pattern as `invites`/`users.is_platform_admin`.
  - **Live-tested lesson, fixed in `supabase/migrations/20260822193000_fix_clients_sites_assets_column_grants.sql`**: this project's `public` schema grants ALL table privileges to `authenticated`/`anon` by default on every newly created table. A column-restricted `grant insert (subset of columns)` / `grant update (subset of columns)` is purely additive and does **not** revoke the pre-existing unrestricted privilege on the other columns — you must `revoke all on <table> from authenticated;` first, then grant back exactly the intended columns (this is what `users`' `is_platform_admin` lockdown already did correctly in the baseline migration; the first cut of this migration omitted the revoke and was confirmed live to leak column-level INSERT/UPDATE on `created_by`/`organization_id`/`client_id` before the fix). Apply this `revoke all` step for every future tenant-scoped table that needs any column-level write restriction — don't assume a fresh table starts with zero grants for `authenticated`.

## Contacts
- `contacts` — **implemented** (issue #26) in `supabase/migrations/20260823090000_contacts_dependent_reference_lists.sql`, tested in `supabase/tests/database/contacts_dependent_reference_lists_rls.test.sql`. A client's contact persons (multiple per client) — the first concrete application of the "Domain completeness"/"Relational detail pages" standard in `docs/ARCHITECTURE.md` to an existing module:
  - `contacts (id, organization_id, client_id, name, role_item_id, email, phone, is_primary, notes, created_by, created_at, updated_at)`. Same shape/pattern as `sites`: `organization_id` is denormalized from `clients.organization_id` via `client_id` (`derive_contact_organization_id`, mirrors `derive_site_organization_id`, including the cross-org re-parent guard), so RLS stays the same single-column `is_member_of_org(organization_id)`/`is_org_owner(organization_id)` shape.
  - `role_item_id` is a nullable FK into `reference_list_items`, validated by `validate_contact_role_item` to be from that organization's `contact_role` list (seeded per-org: Primary [default], Billing, Site manager, Technical) — same structural style as `validate_asset_reference_items`.
  - At most one `is_primary = true` per `client_id`, enforced by `enforce_single_primary_contact` (auto-unsets the previous primary, mirrors `enforce_single_default_reference_item`) plus a partial unique index (`contacts_one_primary_per_client_idx`) backstop.
  - **RLS/write boundary**: identical to `sites` — select `is_member_of_org`; insert/update/delete `is_org_owner` only (same v1 coarse boundary, same known Planner/Engineer gap noted above for assets).
  - **Done**: surfaces as a `Tabs` entry on the client detail page (`app/(app)/clients/[id]/client-detail.tsx`, `contacts-panel.tsx`), created in-context (client already set) via `contact-form-dialog.tsx` — per "Relational detail pages" in `docs/ARCHITECTURE.md`, not a disconnected top-level route.

## Work Orders
- `work_orders` — **implemented** (issue #13, Phase 2) in `supabase/migrations/20260823120000_work_orders_core.sql`, tested in `supabase/tests/database/work_orders_rls.test.sql`. The first-class job/ticket entity (previously only implicit inside Planning) — supersedes the placeholder note this bullet used to carry:
  - `work_orders (id, organization_id, client_id, site_id, asset_id, assigned_to, title, description, notes, status_id, priority_id, scheduled_at, completed_at, contract_id, source_quote_id, source_activity_id, created_by, created_at, updated_at)`. `organization_id` is denormalized from `clients.organization_id` via `client_id` (`derive_work_order_organization_id`, same shape as `sites`/`contacts`). `site_id`/`asset_id` are both nullable (not every work order is scoped to one specific site/asset) but, when set, are cross-checked against `client_id` (and against each other) by `validate_work_order_relations`: `site_id` must belong to `client_id`; `asset_id` must belong to `client_id` and, if `site_id` is also set, to that same site. `assigned_to` is a nullable FK into `users`, validated by the same trigger to be a member of the work order's own organization (mirrors the cross-org-reference validation style `validate_contact_role_item` uses for reference-list FKs, applied here to a `memberships` check instead). `status_id` (not null, defaults to the org's default `work_order_status` item, folded into `derive_work_order_organization_id` the same way `assets.status_id`'s default is folded into `derive_asset_org_and_client`) and `priority_id` (nullable) are reference-list FKs validated by `validate_work_order_reference_items` (same structural style as `validate_asset_reference_items`). **`contract_id`** (nullable FK into `contracts`) was added by `supabase/migrations/20260823150000_contracts_core.sql` once Contracts landed (issue #33) — deferred from this migration's own design note 5 for exactly that reason; when set, it must belong to the same `client_id` as the work order, extended into the same `validate_work_order_relations` trigger (not a parallel one). **`source_quote_id`** (nullable FK into `quotes`) was added by `supabase/migrations/20260824090000_quotes_core.sql` (issue #16) — see the "Quotes" section below. **`source_activity_id`** (nullable FK into `activities`, `on delete set null`) was added by `supabase/migrations/20260829090000_work_orders_source_activity_id.sql` (issue #87, "Workorder uitbreiding") — closes the "No FK from/to work_orders exists yet" gap the "Activities" section below explicitly flagged as deferred. Traces a work order created via the "Maak werkbon" button on an Activity ("melding") record back to that activity. Same shape and same precedent as `source_quote_id`: when set, must belong to the same `client_id` as the work order, validated by extending (`CREATE OR REPLACE`) the existing `validate_work_order_relations` trigger — not a parallel trigger — with a `23503` (dangling reference) / `23514` (cross-client) check identical in style to the `source_quote_id` one. No stored reverse column on `activities` (a one-to-many from an activity's perspective is fully queryable via `work_orders.source_activity_id`, same reasoning `quotes` has no reverse FK to the work order/contract it converted into). The actual "create this work order pre-filled from this activity" conversion logic is application-layer, out of scope here.
  - **RLS — the first table where the Planner/Engineer split is enforced at the database layer, not deferred to the application layer.** Implements `lib/rbac/permissions.ts`'s `planning` row exactly: **owner**/**planner** CRUD on all rows; **engineer** SELECT/UPDATE limited to rows where `assigned_to = auth.uid()` (no INSERT, no DELETE); **finance**/**administratie** SELECT-only, all rows (not assignment-scoped). This closes the "known, deliberate v1 gap" flagged in `20260822190000_clients_sites_assets.sql` design note 2 — for `work_orders`, not yet for `assets`.
  - **New helper**: `public.current_member_role(org_id uuid) returns membership_role` (`SECURITY DEFINER`, `stable`) — the caller's role in that organization, or `NULL` if they have no membership there. Documented alongside `is_member_of_org`/`is_org_owner` (see `docs/ARCHITECTURE.md`'s "Multi-tenancy & data isolation") as the reusable primitive for any RLS policy that needs to branch on *which* role the caller has, not just whether they're a member/owner — reused (not reinvented) by `contracts`' Finance-CRUD boundary below; Assets' own still-deferred Planner/Engineer split remains the next candidate.

## Contracts
- `contracts` / `contract_assets` — **implemented** (issue #33, Phase 2) in `supabase/migrations/20260823150000_contracts_core.sql`, tested in `supabase/tests/database/contracts_rls.test.sql`. The core business-agreement entity with a client (service contract/maintenance agreement) — the last of the original 6 modules to land, and the SECOND table (after `work_orders`) whose RBAC matrix row is enforced as real RLS via `current_member_role`, with a NEW shape (two roles get full CRUD, not one):
  - `contracts (id, organization_id, client_id, name, type_id, sla_tier_id, billing_terms_id, start_date, end_date, auto_renew, value, notes, created_by, created_at, updated_at)`. `organization_id` is denormalized from `clients.organization_id` via `client_id` (`derive_contract_organization_id`, same shape as `sites`/`contacts`/`work_orders`); the same trigger fills in the organization's default `contract_type` item when `type_id` is omitted on insert (same fold-in-the-derive-trigger pattern as `work_orders.status_id`). `name` is a human-readable contract name/number (not auto-generated). `end_date` is nullable (open-ended contracts are real) but, when set, must be `>= start_date` (`contracts_end_date_after_start_date` check constraint). `value numeric(12,2)` is nullable.
  - `type_id` (not null), `sla_tier_id` (nullable), `billing_terms_id` (nullable) are all reference-list FKs, validated by `validate_contract_reference_items` (same structural style as `validate_asset_reference_items`/`validate_work_order_reference_items`). **`sla_tier_id` is the SECOND pilot of the dependent-reference-list mechanism** (see `docs/ARCHITECTURE.md`'s "Dependent reference lists") — `sla_tier` has `parent_list_key = 'contract_type'`, and `validate_contract_reference_items` additionally checks that the chosen `sla_tier_id` item's `parent_item_id` equals the contract's own `type_id` (mirrors `assets.subtype_id`/`type_id`'s cross-field check exactly). `billing_terms_id` is a third, independent, standalone (non-dependent) reference list.
  - **RLS — implements `lib/rbac/permissions.ts`'s `contracts` row exactly**: **owner** and **finance** both get full CRUD on all rows (a new two-full-CRUD-roles shape, unlike `work_orders`' owner/planner pairing); **planner**/**engineer**/**administratie** are SELECT-only, all rows. Reuses `current_member_role(organization_id) in ('owner', 'finance')` for the write policies — no new helper needed, exactly the reusability `current_member_role` was built for.
  - `contract_assets (contract_id, asset_id, organization_id, created_by, created_at)` — **the first genuine many-to-many join table in this schema** (everything else so far is one-to-many via a denormalized `organization_id`). Primary key is the natural key `(contract_id, asset_id)`, no surrogate `id`. `organization_id` is denormalized from the **contract's** `organization_id` (via `contract_id`); the linked asset must additionally resolve to the same organization AND the same `client_id` as the contract (`validate_contract_asset_relations`) — you cannot link an asset from a different client onto a contract, even within the same organization. Same owner-or-finance write boundary as `contracts` itself ("if you can manage the contract, you can manage its asset links"); no UPDATE support at all (delete + re-insert to change either side of a link).
  - **Reference lists**: `contract_type` (Maintenance [default], Service, Installation, Warranty, flat), `sla_tier` (dependent on `contract_type` — Maintenance: Standard/Priority/Premium; Service: Standard/Express; Installation: Standard/Expedited; Warranty: Standard/Extended; no item marked `is_default` since the single-default-per-*list* mechanism doesn't map cleanly onto "one default tier per contract type"), and `billing_terms` (Monthly [default], Quarterly, Annually, Per-visit, One-time, flat, standalone) — all seeded per organization by extending `seed_default_reference_lists`, with a one-time backfill call for existing organizations in this migration.

## Checklists
- `checklist_templates` / `checklist_template_items` / `work_order_checklists` / `work_order_checklist_items` — **implemented** (issue #14, Phase 2, "Checklists / inspection forms") in `supabase/migrations/20260823210000_checklists_core.sql`, tested in `supabase/tests/database/checklists_rls.test.sql`. Configurable form templates attachable to a work order, filled in by engineers with checkbox/notes completion — **photo attachments and e-signature capture are explicitly OUT of scope for this pass** (a documented follow-up needing Supabase Storage integration — buckets, signed upload URLs, storage RLS — not an oversight; likely lands as a `work_order_checklist_item_photos` child table plus a `signed_off_by`/`signed_off_at`/`signature_url` trio on `work_order_checklists`). Note: `work_orders` has no "type" field, so a checklist's applicability is driven entirely by which template a planner/owner/engineer chooses to instantiate on a given work order, not by any work-order-type matching.
  - **Two reused patterns, no new one invented**: `checklist_templates`/`checklist_template_items` are tenant-configured CONTAINER data with the exact same RLS/grant shape as `reference_lists`/`reference_list_items` (owner configures, any member reads) — not modeled as a reference list itself, since template items carry columns (`is_required`, ordering-as-a-first-class `sort_order`) a picklist item doesn't need. `work_order_checklists`/`work_order_checklist_items` are a Work Order SUB-RESOURCE in the same spirit as `time_entries`, denormalizing `organization_id` from the parent work order — but RLS mirrors `work_orders`' OWN per-role shape exactly (engineer gets no create/delete on either instance table), not `time_entries`' `create_own` carve-out.
  - `checklist_templates (id, organization_id, name, created_by, created_at, updated_at)`. RLS: SELECT any member; INSERT/UPDATE/DELETE owner only (identical to `reference_lists`).
  - `checklist_template_items (id, checklist_template_id, organization_id, label, is_required, sort_order, created_by, created_at, updated_at)` — `organization_id` denormalized from `checklist_templates` via `checklist_template_id` (`derive_checklist_template_item_org`, mirrors `derive_reference_list_item_org`). Same RLS boundary as `checklist_templates`.
  - `work_order_checklists (id, work_order_id, checklist_template_id, organization_id, assigned_to, created_by, created_at)` — at most one per work order (`unique (work_order_id)`). `organization_id` AND `assigned_to` are both denormalized from the parent work order (`derive_work_order_checklist_fields`). **`assigned_to` sync decision**: kept in sync ACTIVELY, not left to drift — `work_orders_sync_checklist_assigned_to` (an `after update of assigned_to on work_orders` trigger) re-writes `work_order_checklists.assigned_to` (and cascades into `work_order_checklist_items.assigned_to`) whenever a work order's assignment changes. Chosen over accepting drift because this denormalized column directly backs an access-control boundary (a stale value would wrongly deny the newly-assigned engineer or wrongly retain the previous one's access), unlike a purely cosmetic denormalized field — the cost (two extra single-row UPDATEs on the uncommon event of reassigning a work order that already has a checklist) is negligible. `checklist_template_id` is nullable (`on delete set null` — the template could later be deleted without destroying the historical instance) and, together with `work_order_id`, is excluded from the UPDATE column grant entirely: this table is close to fully immutable after creation (no legitimate "move this checklist" or "re-template after items are already snapshotted" action; correct a mistake via DELETE + re-INSERT, the same precedent `contract_assets` already established). Net effect: the UPDATE RLS policy exists (matching `work_orders`' shape exactly, ready for a future column) but is currently unreachable for every role alike, by design.
  - **Template-to-instance copy mechanism**: inserting a `work_order_checklists` row with a non-null `checklist_template_id` fires an `after insert ... when (new.checklist_template_id is not null)` trigger (`work_order_checklists_instantiate_items`) that calls `copy_checklist_template_items_to_work_order_checklist(work_order_checklist_id)` (`SECURITY DEFINER`), snapshotting every current `checklist_template_items` row for that template into `work_order_checklist_items` by value (not a live join — later template edits don't retroactively rewrite an in-progress instance). Chosen as a trigger, not a second RPC the API layer must remember to call, so a single `insert into work_order_checklists` always yields a fully-populated checklist.
  - `work_order_checklist_items (id, work_order_checklist_id, template_item_id, organization_id, assigned_to, label, is_required, sort_order, is_checked, checked_by, checked_at, notes, created_by, created_at, updated_at)` — the actual per-work-order checklist state. `label`/`is_required`/`sort_order` are copied BY VALUE at creation and remain independently, client-editable per instance thereafter (an owner/planner can correct an item's text or add a bespoke ad-hoc item, with `template_item_id = null`, beyond what the template had). `template_item_id` (nullable, `on delete set null`) is a historical breadcrumb only, excluded from both INSERT and UPDATE grants — populated only by the SECURITY DEFINER copy function. `checked_by`/`checked_at` are trigger-stamped (`set_checklist_item_checked_fields`, mirrors `set_created_by`'s never-client-suppliable pattern): setting `is_checked = true` stamps `checked_by = auth.uid()`/`checked_at = now()`; setting it back to `false` clears both.
  - **RLS — `work_order_checklists`/`work_order_checklist_items` both implement the same shape, mirroring `work_orders`' own per-role split exactly** (not `time_entries`'): **owner**/**planner** CRUD on all rows; **engineer** SELECT/UPDATE only on rows where `assigned_to = auth.uid()` (no INSERT, no DELETE — creating/deleting a checklist instance or its items is a planner/owner action, matching Work Orders' own create boundary); **finance**/**administratie** SELECT-only, all rows. The real, functional "engineer can update" surface is entirely on `work_order_checklist_items` (checking boxes, editing per-instance notes/label) — see the `work_order_checklists` immutability note above for why that table's own UPDATE is policy-present but grant-unreachable today.
  - **Checklists — the FOURTH table pair with real RLS via `current_member_role`** (issue #14): reuses `work_orders`' OWN per-role shape exactly, deliberately NOT `time_entries`' `create_own` shape, since creating a checklist instance is a planner/owner action here. **Resolved** (issue #14, second stage — `api-backend-engineer`): the flagged mismatch is settled by introducing a **distinct `checklists` module** in `lib/rbac/permissions.ts` (own row: owner/planner CRUD, engineer `read_own`/`update_own` only, finance/administratie read-only), rather than reusing `planning` — `planning`'s engineer row was widened to `create_own` for Time Tracking, and reusing it here would have incorrectly suggested an engineer can create a checklist instance too, which the RLS above does not allow. `checklists` is also registered as its own `FeatureKey`/`SHIPPED_FEATURES` entry in `lib/rbac/features.ts`. Server Actions: `lib/checklist-templates/actions.ts` (template CRUD, gated on the `settings` module — same tier as `reference_lists`, per that module's owner-configures/any-member-reads shape) and `app/(app)/work-orders/checklist-actions.ts` (the work-order-instance CRUD, gated on the new `checklists` module).

The pre-sale proposal builder — a quote is converted into a Work Order/Contract on customer approval. The FIFTH table pair whose RBAC matrix row is real RLS via `current_member_role`, reusing `work_orders`' exact shape (owner/planner CRUD, everyone else read-only, no per-row assignment scoping) rather than `contracts`' owner+finance shape, since a quote isn't yet revenue:

  - **RLS — implements the new `quotes` module exactly like `work_orders`' `planning` row**: **owner**/**planner** CRUD on all rows (`quotes` and `quote_line_items` alike — "if you can manage the quote, you can manage its line items"); **engineer**/**finance**/**administratie** SELECT-only, all rows (no per-row assignment scoping — a quote isn't assigned to one engineer, it's a sales document any team member can see).
  - **Reference list**: `quote_status` (Draft [default] → Sent → Accepted / Rejected / Expired) — flat, seeded per organization by extending `seed_default_reference_lists`, with a one-time backfill call for existing organizations in this migration.
  - **Traceability from conversion**: `work_orders.source_quote_id` and `contracts.source_quote_id` (both nullable FKs into `quotes`, added as plain additive columns on those already-existing, already-locked-down tables) trace a Work Order/Contract created by converting an accepted quote back to that quote. When set, each must belong to the same `client_id` as the work order/contract — `validate_work_order_relations` is extended (`CREATE OR REPLACE`) with this check, and `contracts` gains a brand-new `validate_contract_relations` trigger for it (contracts previously had no relations-style cross-field trigger, only `validate_contract_reference_items` for its reference-list FKs). The actual "convert this quote into a Work Order/Contract" business logic (copying line items, setting status, etc.) is application-layer, not built by this migration.
  - **Quotes — a NEW module, the FIFTH table pair with real RLS via `current_member_role`** (issue #16, Phase 3): **Resolved** (issue #16, second stage — `api-backend-engineer`): a distinct `quotes` module entry has been added to `lib/rbac/permissions.ts`'s `Module` type + `TENANT_PERMISSIONS` matrix (owner CRUD, planner CRUD, engineer/finance/administratie read-only, matching the RLS shape above verbatim) and `"quotes"` has been added to `features.ts`'s `FeatureKey` union + `SHIPPED_FEATURES` set — confirmed present in both files by `qa-reviewer`.

## Articles
- `article_groups` / `articles` / `article_components` — **implemented** (issue #92, "[Story] Artikel database") in `supabase/migrations/20260829100000_articles_core.sql` (follow-up column-grant fix in `supabase/migrations/20260829110000_articles_id_insert_grants.sql`), tested in `supabase/tests/database/articles_rls.test.sql`. The product/part database: a tenant-configurable, unlimited-depth Article Group tree, the article record itself, and a bill-of-materials for composite articles. The SEVENTH table (pair/trio) with real RLS via `current_member_role`, and the FIRST with the **owner-or-administratie** full-CRUD shape (`contracts`' owner-or-finance boundary's sibling, same `current_member_role(organization_id) in (...)` primitive, different two-role pairing):
  - `article_groups (id, organization_id, parent_group_id, name, sort_order, created_by, created_at, updated_at)` — a DEDICATED, self-referential tree table (`parent_group_id` references `article_groups.id`), not a `reference_lists` entry: the generic dependent-list mechanism (`parent_list_key`/`parent_item_id`) is single-parent and cross-list only, and `reference_lists_no_self_parent` explicitly forbids a list depending on itself, so it structurally cannot express one self-referential tree within a single list. `organization_id` is supplied directly on insert and checked by RLS (like `reference_lists.organization_id`/`asset_models.organization_id`), since a group's only real parent (`parent_group_id`) is itself organization-scoped data, not one unambiguous row to denormalize from. `validate_article_group_parent` (BEFORE INSERT/UPDATE OF `parent_group_id`) rejects a cross-organization parent, a direct self-reference, and any cycle (walks the ancestor chain, depth-capped at 1000) — DB-level cascade integrity, not left to the UI.
  - `articles (id, organization_id, article_number, description, ean, gtin, mpn, image_url, unit_item_id, manufacturer_item_id, group_id, purchase_price, sale_price, vat_rate_item_id, is_composite, is_active, created_by, created_at, updated_at)` — a DEDICATED table (not a `reference_list_items` row), same reasoning `asset_models` documents: far more structured columns than the generic value/label/color/sort_order/is_default shape supports, plus simultaneous FK relationships into three reference lists (unit/manufacturer/vat rate) and one dedicated table (group). `unique (organization_id, article_number)`. `unit_item_id`/`vat_rate_item_id` are required but may be omitted on INSERT — `derive_article_defaults` fills them from the organization's default `article_unit`/`vat_rate` item (mirrors `assets.status_id`'s fill-in-the-default UX). `manufacturer_item_id`/`group_id` are nullable. All four FKs (list_key + organization match for the three reference-list FKs; organization match for `group_id` against `article_groups`) are validated by `validate_article_reference_items` (same structural style as `validate_asset_model_reference_items`). `is_active boolean not null default true` is a plain column, not a reference list (a genuine tenant-invariant binary, same reasoning as `organizations.is_active`). **Per the product owner's confirmed decision, `purchase_price`/`sale_price` are always this article's own manually-entered columns, even when `is_composite = true`** — `article_components` never drives pricing; it exists for reference/stock/reporting only.
  - `article_components (id, organization_id, parent_article_id, component_article_id, quantity, created_by, created_at, updated_at)` — the composite bill-of-materials. `organization_id` is denormalized from `parent_article_id` (`derive_article_component_organization_id`, mirrors `derive_contact_organization_id`, including the cross-org re-parent guard). `unique (parent_article_id, component_article_id)`; `quantity numeric(12,3)` (fractional quantities allowed) must be `> 0`; a row cannot self-reference (`article_components_no_self_reference`). **Nested composites are disallowed at the DB layer**: `validate_article_component` requires `parent_article_id` to resolve to an article with `is_composite = true` and `component_article_id` to resolve to one with `is_composite = false` — together this structurally forbids any BOM depth beyond one level and sidesteps needing general cycle-detection. A companion trigger on `articles` itself, `validate_article_is_composite_flip` (BEFORE UPDATE OF `is_composite`), closes the remaining loophole: flipping an already-in-use *component* article's own `is_composite` to `true` after the fact, which would otherwise create a de facto nested composite without ever touching `article_components` directly. `parent_article_id`/`component_article_id` are insert-only (excluded from the UPDATE grant, same "delete + re-insert to change either side" stance as `contract_assets`/`quote_line_items`'s immutable-parent columns) — only `quantity` is editable in place.
  - **RLS — the new owner-or-administratie shape**: **owner** and **administratie** both get full CRUD on all three tables (`current_member_role(organization_id) in ('owner', 'administratie')`); every other role (planner/engineer/finance) is SELECT-only, all rows — matching the story's "Owner/Administratie beheren de artikel database" plus the forward-looking need for every other role to at least read Articles data. The three new reference lists below stay under the *existing* `reference_lists`/`reference_list_items` table-wide RLS (owner-only write) — no RLS change was needed there.
  - **Reference lists**: `article_unit` (Stuk [default], Liter, Kg — flat), `article_manufacturer` (deliberately minimal: a single "Other" [default] catch-all, since a tenant's parts manufacturers are genuinely open-ended and specific to what they stock, unlike `asset_brand`'s printer-vertical seed), and `vat_rate` (0%, 9%, 21% [default, the Dutch standard rate] — `value` stores the literal numeric percentage as text, e.g. `'21'`, not a slug, so application code can do `Number(item.value)` directly for tax math in future invoicing work instead of maintaining a separate mapping) — all flat (no `parent_list_key`), seeded per organization by extending `seed_default_reference_lists`, with a one-time backfill call for existing organizations in this migration.
  - **Live-tested lesson, fixed in `supabase/migrations/20260829110000_articles_id_insert_grants.sql`**: Postgres requires column-level INSERT privilege for `id` the moment a caller supplies an explicit value for it (not just relying on `DEFAULT`), even though the column has `default gen_random_uuid()` — the "receives its value from a column default" carve-out only applies when the column is omitted from the INSERT entirely (or given the keyword `DEFAULT`). This module's own migration, like several existing ones (`asset_models`, `account_managers`), never explicitly granted `insert (id)`. Granting it is a deliberate, harmless widening (RLS still fully gates who may insert a row at all) — flagged as a likely-latent gap on those other tables too, for a future sweep.
  - **Articles — a NEW module, the SEVENTH table (pair/trio) with real RLS via `current_member_role`**: `lib/rbac/permissions.ts` needs a new `"articles"` module entry (owner/administratie CRUD, planner/engineer/finance read-only) and `lib/rbac/features.ts` needs a corresponding `FeatureKey`/`SHIPPED_FEATURES` entry, plus a nav item — none of that is done by this migration (schema/RLS only); flagged for `auth-rbac-engineer` and `api-backend-engineer`/`frontend-ui-engineer` to build on top of this exact shape.

## Assets: auto-generated Asset ID (issue #105)
- `assets.name` (the "Asset ID" field in the UI) — **stays `not null`**, but is no longer required from the caller. `supabase/migrations/20260831090000_assets_auto_generate_asset_id.sql` adds a BEFORE INSERT trigger (`assets_set_default_asset_name` / `assign_default_asset_name()`) that fills `new.name` with the next sequential `AST-NNNNN` id (5-digit zero-padded, e.g. `AST-00042`) for the asset's own organization whenever the caller leaves it null or blank — never overrides an explicit name.
- Race-safety: a naive `select max(name)` + 1 is unsafe under concurrent inserts. Instead, a new per-organization counter table, `asset_id_sequences (organization_id primary key, last_number)`, is advanced atomically by `next_asset_display_id(organization_id)` via a single `insert ... on conflict (organization_id) do update ... returning` statement — Postgres's row lock on the target counter row serializes concurrent inserts within the same organization; different organizations never contend (separate counter rows).
- `asset_id_sequences` has RLS enabled + forced with **zero policies and zero grants to `authenticated`** — it is not a tenant-readable entity, only reachable via `next_asset_display_id()` (`SECURITY DEFINER`, same pattern as `derive_asset_org_and_client`/`set_created_by`). No new RBAC matrix row: this is plumbing behind the existing Assets write boundary, not a new module/action.
- Trigger ordering: `assign_default_asset_name()` needs `new.organization_id`, which `assets_derive_org_and_client` resolves first — guaranteed by Postgres's alphabetical same-timing trigger order (`assets_derive_org_and_client` < `assets_set_default_asset_name`), the same trick `20260826170000_assets_external_reference_brand_model.sql` already documents for `assets_validate_reference_items`. Deliberately kept as its own dedicated `BEFORE INSERT`-only trigger (not folded into `derive_asset_org_and_client` the way the `status_id` default was) so it can never fire on the `UPDATE OF site_id` re-parent path and silently overwrite an existing asset's name.
- Tested in `supabase/tests/database/clients_sites_assets_rls.test.sql` (tests 83-93): omitted-name and blank-name auto-generation, explicit name never overridden, per-organization counter independence (org B's first auto id is also `AST-00001`), and `asset_id_sequences` rejecting direct SELECT/INSERT from an authenticated role. Not yet run against a real Postgres — `supabase test db` requires Docker, unavailable in the agent environment that authored it; reviewed by careful manual inspection instead (`db-schema-architect`, hand off to `qa-reviewer` to actually run the suite).
- Follow-up for `api-backend-engineer` (not done here): `app/(app)/assets/schema.ts`'s `name` field should become `.optional()` on the create path so the Zod layer stops rejecting an omitted Asset ID before the request reaches the DB.

## Activity Notes + Activity Events (Melding detail redesign)
- **Schema**: `supabase/migrations/20260902090000_activity_notes_and_events.sql`, tested in `supabase/tests/database/activity_notes_and_events_rls.test.sql` (33 assertions). Backs the redesigned `/activities/[id]` detail page's Notes and Historie sections (`.design-handoff/melding_detail/README.md`).
- **`activity_notes`** — free-text, user-authored notes on an activity. `organization_id` AND `action_holder_id` are both denormalized from the parent `activities` row (via `activity_id`) by `derive_activity_note_fields` (`BEFORE INSERT`, mirrors `derive_activity_organization_id`'s cross-table-lookup style but reading `activities` instead of `clients`) and excluded from the INSERT column grant entirely. `body` has two CHECK constraints (`activity_notes_body_not_blank`, `activity_notes_body_max_length` — 5000 chars, same ceiling as `activities.description`'s Zod max). - **`activity_events`** — append-only, append-ONLY-by-trigger history/audit timeline. All three event triggers are `SECURITY DEFINER`, so their `INSERT`s succeed regardless (the function-owner role has `BYPASSRLS` and full table privileges independent of any grant to `authenticated`) — the exact mechanism `20260901090000_work_order_auto_draft_quotes.sql` already established for `create_work_order_auto_draft_quote`/the `sync_*_to_auto_draft_quote` triggers. This is the option the task brief offered over a permissive `WITH CHECK (true)` INSERT policy, chosen because "no grant exists" is unreachable by ANY direct client statement, not merely one that happens to fail a values check.
- **Denormalized `action_holder_id`, actively kept in sync (not display-only)**: both tables carry their own `action_holder_id`, since `activities.action_holder_id` is editable after creation and this column backs each child table's own RLS visibility boundary — exactly the precedent `work_order_checklists`/`work_order_checklist_items` already set for `assigned_to` (see the "Checklists" section above, design note 2 in that migration). `sync_activity_dependents_action_holder` (`AFTER UPDATE OF action_holder_id` on `activities`, `WHEN` guarded to an actual change) actively re-syncs BOTH tables (mirrors `sync_work_order_checklist_assigned_to`, fanned out to two targets instead of one) — a stale copy would silently leak a note/event to the old action holder or hide it from the new one. Verified by the RLS test: reassigning the fixture activity from engineer A to engineer A2 flips visibility of a pre-existing note and a pre-existing `created` event in the same transaction.
- **RLS shape mirrors `activities` itself**, not a fresh matrix row — no new RBAC matrix entry: owner/planner see & write (create, for notes) any row; engineer scoped to `action_holder_id = auth.uid()`; finance/administratie read-only, all rows; tenant-isolated via `is_member_of_org(organization_id)`.

## Work Order auto-draft Quote: freeze rates at time-of-registration (issue #109)
- **Schema**: `supabase/migrations/20260901090000_work_order_auto_draft_quotes.sql`, tested in `supabase/tests/database/work_order_auto_draft_quotes_rls.test.sql` (46 assertions). Solves: today's Work Order cost display is computed at "Create Quote" time using WHATEVER rates apply then, not the rates that applied when the work was actually done — a fault worked on 31 Dec must bill at 31-Dec rates even if the quote is finalized 5 Jan after a rate change.
- **`organizations.default_travel_article_id`/`default_work_article_id`** (nullable FK into `articles`) — the org-level rate-resolution fallback layer explicitly left "out of scope" by `20260830090000_engineer_client_rate_overrides.sql`'s own comment on `memberships.has_custom_rate`. No override price column at this layer (unlike `clients`/`memberships`' travel/work columns) — the price IS the linked article's own live `sale_price`/`purchase_price`. Validated by a NEW dedicated trigger, `validate_organization_default_rate_articles` (not a reuse of `validate_rate_override_articles` — an `organizations` row's own `id` IS the organization id being checked against, not a separate `organization_id` column). No new GRANT needed (`organizations` has always had a table-wide, not column-level, INSERT/UPDATE grant — same pre-existing scope difference already documented for `memberships`); write access stays gated by the existing `organizations_update_owner` RLS policy.
- **`quotes.is_auto_draft boolean not null default false`** — marks a quote as the system-managed 1:1 shadow of a work order, distinct from `status_id = Draft` (which also covers human-authored draft quotes). At most one per `work_order_id` (`quotes_one_auto_draft_per_work_order_idx`, a partial unique index); requires `work_order_id` to be set (`quotes_auto_draft_requires_work_order` CHECK). Excluded from the INSERT column grant (only the new `work_orders_create_auto_draft_quote` trigger ever sets it true) but included in the UPDATE grant, since flipping it false is exactly what a future "Create Quote" promotion action needs to do as an ordinary owner/planner UPDATE — no new RLS tier.
- **`quote_line_items.purchase_price numeric(12,2)`** — a new STORED snapshot column (nullable), unlike every other purchase-price lookup in this schema which reads `articles.purchase_price` live. Null/unused for a human-authored line item (unchanged path); frozen at sync time for an auto-draft-owned line item, same historical-accuracy reasoning as `unit_price`. Plus two new sync-identity columns, `source_time_entry_id`/`source_work_order_article_id` (nullable FKs, `on delete set null`, mutually exclusive via a CHECK), each with a partial unique index — what makes the sync triggers' upsert idempotent (one line item per source row) and doubles as their FK/filter index.
- **Auto-draft creation**: `work_orders_create_auto_draft_quote`, `AFTER INSERT` on `work_orders`, `SECURITY DEFINER` — makes it impossible to create a work order without its auto-draft, regardless of which Server Action performs the insert. The INSERT into `quotes` succeeds despite `is_auto_draft` being withheld from the client-facing grant and regardless of the inserting role's own `quotes` RLS privileges, because a `SECURITY DEFINER` function's DML executes under the function owner's privileges (bypassing both RLS and column grants) — the same mechanism every other `SECURITY DEFINER` trigger in this schema already relies on. Quote name mirrors `createQuoteFromWorkOrder`'s own `"Quote — {title}"` pattern.
- **`resolve_billing_rate(organization_id, client_id, user_id, is_travel)`** — the shared 4-layer rate-resolution function, SQL-callable (`STABLE` + `SECURITY DEFINER`, `revoke ... grant execute to authenticated`): client `has_custom_rate` override → engineer (`memberships`) `has_custom_rate` override → `organizations.default_travel_article_id`/`default_work_article_id` (that article's own live price) → unresolved (zero rows, no exception — the issue brief is explicit an unresolved rate must be queryable by a later UI, not a hard failure). Unlike this schema's internal-only `validate_*`/`derive_*` helpers, this one is genuinely meant to be called directly (by the sync triggers below, and by a future application-layer preview) — that direct callability is exactly why it opens with an `is_member_of_org(p_organization_id)` guard (`42501` otherwise): without it, a bare `SECURITY DEFINER` function taking an arbitrary `p_organization_id` parameter would let any authenticated user on any tenant read back another tenant's rate-override data.
- **Sync triggers** — `time_entries`/`work_order_articles` each get TWO triggers, not one, split by timing: a `BEFORE DELETE` trigger (deletes the matching line item, only while the owning quote is still `is_auto_draft`) plus an `AFTER INSERT OR UPDATE` trigger (upserts it). This split exists specifically to avoid a real ordering bug: `quote_line_items.source_time_entry_id`/`source_work_order_article_id`'s own `on delete set null` FK is implemented by Postgres as an internal `AFTER`-ROW trigger on the SAME table (`time_entries`/`work_order_articles`); two `AFTER DELETE` triggers on one table fire in alphabetical-by-name order, which is NOT guaranteed to put a user trigger after an auto-generated `RI_ConstraintTrigger_...` one — if the FK's `SET NULL` fired first, an `AFTER DELETE` cleanup here would find its own lookup already nulled out, silently leaving a stale line item behind on a still-active auto-draft instead of deleting it. Running the cleanup `BEFORE DELETE` instead removes the race entirely (the parent row, and therefore the FK action, hasn't happened yet). All four functions are `SECURITY DEFINER` — this is the RLS-sensitive core of the feature: an engineer has INSERT/UPDATE rights on `time_entries`/`work_order_articles` (own rows; no DELETE on either, that stays owner/planner-only) but NO direct write rights on `quotes`/`quote_line_items` at all, and `SECURITY DEFINER` is what lets that engineer's own write transitively reach `quote_line_items` without ever being granted a `quotes` privilege. Scoped strictly to the row being synced — the target quote is looked up SOLELY by the source row's own (already-derived, already-validated) `work_order_id` + the system flag `is_auto_draft = true`, never a client-supplied `quote_id`, and every written value is server-computed (a resolved rate, a live article price, a computed duration), never taken directly from arbitrary client input beyond what existing RLS on the source tables already validated.
  - `time_entries`: excludes Break-type and still-running (`ended_at is null`) entries; computes quantity with the IDENTICAL whole-minute-then-2-decimal-hours rounding `createQuoteFromWorkOrder`'s `computeQuantityHours` uses, so the figure never differs between this always-on sync path and that (still-live, for a second manually-triggered quote) application code path; a rounds-to-zero duration is treated as unresolved. An unresolved rate (layer 4) leaves the entry OFF the auto-draft entirely (same choice `createQuoteFromWorkOrder` already made for its own `skippedTimeEntryIds`) — queryable by joining eligible time entries against `quote_line_items.source_time_entry_id` and finding no match, no extra flag column added. `work_order_id` is NOT immutable on `time_entries` (unlike `work_order_articles`), so an UPDATE that re-parents an entry first cleans up any line item left on the OLD work order's auto-draft.
  - `work_order_articles`: simpler — no client/engineer override layer, price always read straight from the consumed article; a missing `sale_price` defaults `unit_price` to 0 rather than skipping the line (same "visibly wrong-but-present" choice `createQuoteFromWorkOrder` already made). `work_order_id` is immutable here, so no re-parenting case exists.
  - `sort_order` deliberately left at its column default (0) for every sync-inserted line item — maintaining a globally-correct interleaved order across an open-ended incremental stream (rather than `createQuoteFromWorkOrder`'s one-shot batch insert) is real complexity with no payoff yet, since nothing reads/displays these lines in order today; flagged for whoever builds that read to order via a join back to `time_entries.started_at`/`work_order_articles.created_at` through the new `source_*` columns.
- **Application layer, built as follow-up (same issue #109)**: `api-backend-engineer` changed `createQuoteFromWorkOrder` (`app/(app)/work-orders/create-quote-actions.ts`) to promote the existing auto-draft (`is_auto_draft -> false` via `promoteAutoDraftQuote`, scoped `.eq("is_auto_draft", true)` so a concurrent double-click no-ops instead of double-processing) instead of always inserting a new quote, falling back to the original from-scratch build only when no auto-draft exists (legacy pre-migration work orders); added `getWorkOrderCostSummary`/`getUnresolvedWorkOrderTimeEntries` (`app/(app)/work-orders/quote-sync-actions.ts`, gated `can(actor, "planning", "read")` — excludes engineer) and `getOrganizationDefaultRateSettings`/`updateOrganizationDefaultRateSettings` (`app/(app)/settings/organization-rate-actions.ts`, update gated owner-only). `frontend-ui-engineer` then built: a Settings > Billing > Default Rates page (`app/(app)/settings/default-rates/`, read-only summary for non-owners); the Work Order Hours section now shows a cost per bucket plus an unresolved-rate `Callout` warning, and the "To invoice" KPI tile reads the real frozen total (falls back to material-only for engineers, "Already quoted" post-promotion) — both in `app/(app)/work-orders/components/`; and the `/quotes` list (`app/(app)/quotes/components/`) filters out `is_auto_draft` quotes by default with a toggle + "Concept" badge when shown.
- Not yet run against a real Postgres — `supabase test db` requires Docker, unavailable in every agent environment that has touched this feature so far (schema authoring and the `qa-reviewer` pass alike). Reviewed by careful manual inspection instead each time (including the FK-firing-order reasoning above, which was caught and fixed during the original review, not by an actual test run; `qa-reviewer` separately re-traced the RLS/SECURITY DEFINER path end-to-end and found no correctness issues). **Still an open gap against this repo's Definition of Done ("RLS policy exists and is tested") — run `supabase/tests/database/work_order_auto_draft_quotes_rls.test.sql` for real via `supabase test db` (needs Docker or CI) before treating this as fully regression-covered.**

- **Planning row — enforced at the RLS layer, not just the application layer** (issue #13): `work_orders` is the first module where this matrix's row is implemented as real Postgres RLS policies (via the new `current_member_role` helper), not only as the application-level `can()` check.
